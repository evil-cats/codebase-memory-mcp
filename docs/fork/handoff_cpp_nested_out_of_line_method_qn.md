# Handoff: out-of-line методы вложенных классов C++ не теряются из графа

Статус: исправление реализовано; узкие и связанные проверки пройдены, полный
`gate` ограничен известными блокерами окружения и статического анализа.
Дата обнаружения: 2026-09-04.
Ветка: `v0.10.8-lora`.
Текущий коммит ветки на момент диагностики:
`69752b3b42b29ced0aa957df2e3e557514c7c372`.
Текущая upstream-база: `v0.10.8`
(`46ae198fc11cda80e817acbc5f5908d7c2de7032`).

## Назначение

Исправить извлечение out-of-line методов вложенных классов C++ и CUDA. Определения
вида `Outer::Inner::method()` и более глубокие цепочки, записанные относительно
уже активной лексической области namespace, должны создавать узлы `Method`,
сохранять полный QN класса-владельца и согласованно атрибутировать вызовы и
семантические записи внутри метода.

Глубина владельца не должна быть ограничена двумя, тремя или четырьмя уровнями.
Алгоритм должен обходить всю структурную цепочку `qualified_identifier` до
конечного имени вызываемого символа в пределах общего защитного ограничения
глубины AST.

Карточка предназначена для агента без контекста текущего разговора. Она содержит
живое воспроизведение, первопричину, красную фазу, требуемое исправление, тесты,
критерии готовности и границы работы.

Связанный предшествующий handoff:
[namespace владельца out-of-line метода](handoff_cpp_out_of_line_method_namespace_qn.md).
Он исправил сохранение лексического namespace для формы `Class::method()`, но не
покрыл вложенный класс в `Class::Nested::method()`.

Дефект подтверждён на полном индексе проекта:

```text

root_path:
```

На момент диагностики `index_status` возвращал `status: ready`. Для обоих файлов
примера `check_index_coverage` не показывал записанных `parse_partial` или
`skipped`-пробелов:

```text

libs/sniper/graphite/Graphite.cpp
```

В `Graphite.h:28-49` существует вложенный класс:

```cpp
struct GraphitePromise
{

```

В `Graphite.cpp:50-68` находятся обе out-of-line реализации:

`get_code_snippet` для этого QN показывает конструктор и `release()`, потому что


Поиск всех символов `Graphite.cpp` находит методы внешнего `Graphite`, начиная с

относит совпадения к узлу `Module`, поскольку отдельных узлов вызываемых символов

```text
libs.sniper.graphite.Graphite.sniper.graphite.Graphite.GraphitePromise.release()
```

Оба узла должны иметь `label: Method` и `parent_class`, точно равный QN
`GraphitePromise`.

## Фактическая форма AST

Локальная проверка выполнена той же vendored-грамматикой tree-sitter-cpp,
которую использует индексатор. Для `Graphite::GraphitePromise::release()` она
создаёт правовложенную структуру:

```text
function_definition
└── function_declarator
    └── declarator: qualified_identifier
        ├── scope: namespace_identifier "Graphite"
        └── name: qualified_identifier
            ├── scope: namespace_identifier "GraphitePromise"
            └── name: identifier "release"
```

Конструктор имеет ту же форму: конечный `identifier "GraphitePromise"` также
находится во внутреннем `qualified_identifier`.

Каждый дополнительный квалификатор добавляет ещё один вложенный узел:

```text
A::B::method()       -> A -> B -> method
A::B::C::method()    -> A -> B -> C -> method
A::B::C::D::method() -> A -> B -> C -> D -> method
```

Следовательно, специальная обработка ровно двух или четырёх уровней не исправит
класс дефектов.

В показанном AST tree-sitter помечает `Graphite` и `GraphitePromise` одинаковым
видом `namespace_identifier`, хотя первый является внешним классом, а второй —
вложенным. Поэтому один только вид узла не позволяет отличить namespace от
уровня класса. В обязательном сценарии этой карточки namespace уже задан
лексическими предками `function_definition`, а вся явная цепочка
`Graphite::GraphitePromise` является относительным владельцем метода.

У полностью квалифицированной формы на уровне файла, например
`ns::detail::Outer::Inner::method()`, этой границы в локальном AST нет. Её
разрешение требует семантического сопоставления с известными классами и является
отдельной задачей, а не поводом угадывать число namespace или классов.

## Первопричина

### Конечное имя ищется только среди непосредственных детей

`cbm_resolve_c_declarator_name_node()` в
`internal/cbm/helpers.c:1069-1090` доходит до внешнего `qualified_identifier` и
передаёт его в `resolve_qualified_name()` на строках `1054-1065`.

`resolve_qualified_name()` последовательно вызывает `cbm_find_child_by_kind()`
для `operator_name`, `operator_cast`, `destructor_name`, `identifier` и
`field_identifier`. `cbm_find_child_by_kind()` проверяет только непосредственных
детей переданного узла.

Для `Graphite::release()` внешний узел содержит конечный `identifier` напрямую,
поэтому существующий код работает. Для `Graphite::GraphitePromise::release()`
его непосредственное поле `name` является ещё одним `qualified_identifier`.
Конечный `identifier "release"` находится уровнем глубже и не обнаруживается.

`cbm_resolve_c_declarator_name_node()` возвращает пустой `TSNode`, а
`extract_func_def()` завершает работу до создания `CBMDefinition`. Поэтому узел
не получает даже ошибочный QN: определения `Method` в графе нет совсем.

### Владелец также обрезается до первого уровня

Одного исправления поиска имени недостаточно. `cpp_out_of_line_scope_text()` на
`internal/cbm/helpers.c:494-521` находит тот же внешний `qualified_identifier`,
читает только его непосредственное поле `scope` и возвращает `Graphite`.

Для вложенного определения полный владелец находится во всей цепочке перед
конечным именем метода:

```text
Graphite::GraphitePromise
```

Если исправить только имя, `cbm_cpp_out_of_line_owner_qn()` привяжет метод к
внешнему `Graphite`, а не к `GraphitePromise`. Узел появится с неверными
`parent_class`, `qualified_name` и `DEFINES_METHOD`.

### Ошибка расходится по трём путям QN

Общий дефект влияет на три потребителя:

1. `extract_func_def()` на `internal/cbm/extract_defs.c:3474-3699` создаёт
   `Method`, его `qualified_name` и `parent_class`.
2. `compute_func_qn()` на `internal/cbm/extract_unified.c:697-901` использует тот
   же `cbm_resolve_func_name()` для
   `CBMCall.enclosing_func_qn`. При пустом имени область функции не создаётся.
3. `cbm_enclosing_func_qn()` на `internal/cbm/helpers.c:1893-1985` получает имя
   через `func_node_name()`, который для C/C++/CUDA вызывает тот же
   `cbm_resolve_c_declarator_name_node()`. При неудаче функция возвращает QN
   модуля для использований, чтений, записей и других семантических записей.

После исправления все три пути обязаны использовать одну и ту же декомпозицию
AST. Появления только узла `Method` недостаточно.

### Декларации в заголовке не служат резервным источником

Конструктор на `Graphite.h:30` разобран как `declaration`, а `release()` на
`Graphite.h:48` — как `field_declaration`. Оба содержат вложенный
`function_declarator`.

`resolve_method_name()` в `internal/cbm/extract_defs.c:4519-4589` вызывает общую
функцию разрешения семейства C только для `function_definition`. Для C++
`declaration` и `field_declaration` подходящей резервной ветки нет, поэтому
декларации также не создают узлы `Method`.

Это объясняет полное отсутствие методов, но расширение модели графа до
узлов вызываемых символов только по декларациям не требуется для исправления
текущего дефекта. Каноническим источником существующего метода остаётся его
out-of-line определение с телом.

## Почему существующие тесты не поймали дефект

`repro_issue554_cpp_out_of_line_method_class_qualified` использует только:

```cpp
void Foo::bar() {}
```

`cpp_out_of_line_method_preserves_lexical_namespace` использует:

```cpp
bool AdcampRequest::parse() const {}
```

В обоих случаях перед методом находится один квалификатор класса, а конечное имя
является непосредственным ребёнком внешнего `qualified_identifier`.

Тесты вложенных C++-классов в `tests/test_c_lsp.c` используют методы с телами
непосредственно внутри класса. Они проверяют другой AST-путь и не воспроизводят
определение `Outer::Inner::method()` вне класса.

## Минимальное локальное воспроизведение

Добавить детерминированный пример без зависимости от DSP:

```cpp
namespace app {

bool enabled = true;
int helper() { return 1; }

struct Outer {
    struct Inner {
        Inner();
        void run();

        struct Deep {
            struct Deeper {
                void ping();
            };
        };
    };
};

Outer::Inner::Inner() {}

void Outer::Inner::run() {
    enabled = helper() != 0;
}

void Outer::Inner::Deep::Deeper::ping() {
    enabled = helper() != 0;
}

} // namespace app
```

Пример проверяет конструктор и обычный метод на двух уровнях владельца, а также
обычный метод на четырёх уровнях. Четырёхуровневый случай является защитой от
локального исправления только реального примера `Graphite`; контракт всё равно
остаётся неограниченным конкретным числом уровней.

Для файла `nested.cpp` ожидаемые владельцы:

```text
nested.app.Outer.Inner
nested.app.Outer.Inner.Deep.Deeper
```

Ожидаемые методы:

```text
nested.app.Outer.Inner.Inner()
nested.app.Outer.Inner.run()
nested.app.Outer.Inner.Deep.Deeper.ping()
```

## Контракт после исправления

Для C++ и CUDA должны выполняться следующие инварианты:

1. Любая цепочка класса-владельца `A::B::...::method`, относительная к уже
   вычисленной лексической области namespace, создаёт один узел `Method`.
2. Конечное имя вызываемого символа извлекается из самого внутреннего поля
   `name`, а не из заранее выбранного уровня дерева.
3. Полный QN владельца содержит все области перед конечным именем метода в
   исходном порядке.
4. Лексический namespace добавляется ровно один раз и не заменяется первым
   явным квалификатором.
5. `method.parent_class` точно равен `class.qualified_name` вложенного класса.
6. `method.qualified_name` начинается с `class.qualified_name + "."` и сохраняет
   каноническую C++-сигнатуру.
7. `CBMCall.enclosing_func_qn` внутри метода точно равен QN этого метода.
8. `CBMUsage`, `CBMReadWrite` и другие реально созданные семантические записи
   внутри метода используют тот же `enclosing_func_qn`.
9. Полный конвейер создаёт точное ребро
   `Class -[:DEFINES_METHOD]-> Method`.
10. Одноуровневые out-of-line методы, namespace, конструкторы, деструкторы,
    операторы, шаблоны, перегрузки и cv/ref-квалификаторы сохраняют прежнюю
    идентичность.
11. Последовательный, параллельный и инкрементальный пути получают одинаковые QN.
12. Исправление не зависит от имён `Graphite`, `GraphitePromise`, `release` или
    каталогов DSP.
13. Существующие полностью квалифицированные определения с одним сегментом
    класса, например `ns::detail::Class::method()`, сохраняют действующий формат
    namespace и прежний QN.

## Требуемое устройство исправления

### Единая декомпозиция квалифицированного вызываемого символа

Добавить общую вспомогательную функцию C++/CUDA, которая по
`function_definition` или найденному `qualified_identifier` структурно
возвращает:

- конечный узел имени вызываемого символа;
- полную последовательность областей владельца перед этим именем;
- признак того, что символ действительно является out-of-line методом.

Точная сигнатура может следовать стилю проекта. Существенно, чтобы один результат
использовали и функция разрешения имени, и `cbm_cpp_out_of_line_owner_qn()`.

Обход должен следовать именованным полям `scope` и `name`, пока `name` остаётся
`qualified_identifier` или `scoped_identifier`. Конечными именами должны
оставаться поддерживаемые текущим кодом виды:

- `identifier` и `field_identifier`;
- `destructor_name`;
- `operator_name` и `operator_cast`;
- другие уже поддерживаемые виды конечного имени без регрессии.

Нельзя разбирать сырой текст простым `strrchr("::")`: шаблонные аргументы,
операторы и вложенные типы могут содержать собственные квалификаторы. AST уже
задаёт границу между `scope` и `name`.

Декомпозиция AST должна вернуть последовательность областей без вывода по виду
`namespace_identifier`. В обязательном сценарии уже вычисленная лексическая
область задаёт namespace, поэтому все элементы относительной цепочки владельца
нужно добавить к ней как уровни классов в исходном порядке. Именно здесь нельзя
считать классом только последний сегмент: это снова потеряет вложенные классы.

Для определения на уровне файла с явной смесью namespace и вложенных классов
такого основания нет. Нельзя безусловно заменить все `::` точками: это изменит
действующий компактный формат многоуровневого namespace. Нельзя и угадывать
границу по регистру имени, числу сегментов или их видам AST. Эта карточка требует
сохранить прежнее поведение формы `ns::detail::Class::method()`, но не расширяет
исправление до семантического разрешения формы
`ns::detail::Outer::Inner::method()`.

Защитное ограничение от патологической глубины допустимо, но оно должно быть
общим пределом безопасности AST, а не функциональным пределом в два или четыре
уровня. При его достижении извлечение должно завершаться безопасно и не создавать
частичный QN как достоверный.

### Подключение общего результата

- `cbm_resolve_c_declarator_name_node()` должен получать конечное имя из общей
  декомпозиции.
- `cpp_out_of_line_scope_text()` следует удалить, сузить либо перевести на тот же
  общий результат; второго независимого алгоритма обхода оставаться не должно.
- `cbm_cpp_out_of_line_owner_qn()` должен строить QN из всей цепочки владельца и
  уже вычисленной лексической области.
- `extract_func_def()`, `compute_func_qn()` и `cbm_enclosing_func_qn()` должны
  получить идентичные базовые QN до применения `cbm_cpp_callable_identity()`.
- Декларации и комментарии в `internal/cbm/helpers.h` нужно обновить, если
  меняется доступный внутренним модулям контракт вспомогательной функции.
- Ветка определения с полным квалификатором на уровне файла должна сохранить
  существующее поведение и формат QN; рекурсивный обход имени не должен случайно
  превратить все namespace в точечные сегменты классов.

### Недопустимые обходы

Не исправлять дефект следующими способами:

- добавить отдельную ветку только для двух, трёх или четырёх уровней;
- искать `GraphitePromise` или `release` по тексту;
- привязать метод к первому либо последнему короткому имени класса без полного
  QN;
- создать alias-узел вложенного класса с укороченным QN;
- ослабить точное создание `DEFINES_METHOD` до поиска по суффиксу;
- исправить только `search_graph` или отображение `get_code_snippet`;
- исправить только узел `Method`, оставив вызовы и использования с QN модуля;
- индексировать все declaration-only методы лишь как обход потери определения;
- добавить специальное правило для `.cpp`, `libs/sniper` или DSP.

## Обязательные регрессионные тесты

### Красная фаза извлечения

В `tests/test_extraction.c` рядом с
`cpp_out_of_line_method_preserves_lexical_namespace` добавить и зарегистрировать
тест `cpp_out_of_line_nested_class_preserves_all_owner_levels` на минимальном
примере этой карточки.

До изменения рабочего кода тест должен падать как минимум потому, что методы
`Inner`, `run` и `ping` отсутствуют в `r->defs`. Красную фазу нужно выполнить и
зафиксировать до реализации.

Тест обязан:

1. Проверить `has_error == false` и `parse_incomplete == false`.
2. Найти точные QN `nested.app.Outer.Inner` и
   `nested.app.Outer.Inner.Deep.Deeper`.
3. Найти ровно по одному ожидаемому конструктору, `run()` и `ping()`.
4. Проверить точное равенство каждого `parent_class` QN соответствующего класса.
5. Проверить полные QN методов, включая канонические сигнатуры.
6. Проверить вызов `helper()` внутри `run()` и `ping()` с точным
   `enclosing_func_qn` метода. Это защищает `compute_func_qn()`.
7. Проверить детерминированно создаваемую запись для `enabled` с тем же
   `enclosing_func_qn`. Это защищает `cbm_enclosing_func_qn()`.
8. Убедиться, что не созданы методы с владельцами только `Outer`, `Inner` либо
   `Deeper` без полной цепочки.

Та же общая вспомогательная функция работает для CUDA. Добавить параметризованный
прогон эквивалентного примера с `CBM_LANG_CUDA` и путём `nested.cu` либо отдельную

## Результат реализации

Исправление реализовано в `internal/cbm/helpers.c` и
`internal/cbm/helpers.h`. Общая структурная декомпозиция декларатора теперь:

- проходит обёртки декларатора;
- рекурсивно следует правовложенным полям `scope` и `name` у
  `qualified_identifier` и `scoped_identifier`;
- возвращает конечное имя и все уровни владельца одним результатом;
- при достижении `CBM_DECLARATOR_DEPTH_LIMIT` отвергает разбор целиком, не
  публикуя частичный QN.

Эту декомпозицию совместно используют
`cbm_resolve_c_declarator_name_node()` и `cpp_out_of_line_scope_text()`, поэтому
определения, вызовы и семантические записи получают одинаковую основу QN.

Добавлены обязательные регрессии:

- `cpp_out_of_line_nested_class_preserves_all_owner_levels` в
  `tests/test_extraction.c` для C++ и CUDA, конструктора, методов с двумя и
  четырьмя уровнями владельца, точных `parent_class`, вызовов и записей;
- `es_defines_method_cpp_out_of_line_nested_class` в
  `tests/test_edge_structural.c` для точного ребра `DEFINES_METHOD` и отсутствия
  укороченных или повторённых QN.

## Критерии готовности

- Новые C++ и CUDA тесты падают до исправления и проходят после него.
- Обход поддерживает произвольную длину относительной цепочки класса-владельца в
  пределах общего защитного ограничения глубины AST, без специальных веток по
  числу уровней.
- Конструктор и обычный метод вложенного класса создаются как `Method`.
- Полный QN владельца одинаков в определениях, вызовах и семантических записях.
- `parent_class` точно совпадает с QN вложенного `Class`.
- Полный конвейер создаёт точное `DEFINES_METHOD`.
- Одноуровневые out-of-line методы, namespace, перегрузки и специальные формы
  вызываемых символов C++ не получили регрессий.
- Узкие и полные тесты, lint, Markdown-lint и `git diff --check` прошли либо для
  каждой непройденной обязательной проверки зафиксирована блокирующая причина.
- Исходники DSP не изменялись.
- Установка, перезапуск и переиндексация не выполнялись без отдельного разрешения.

## Восстановление после обновления upstream

После обновления сначала проверить:

1. как `cbm_resolve_c_declarator_name_node()` получает конечное имя вызываемого
   символа;
2. как `cbm_cpp_out_of_line_owner_qn()` собирает все уровни владельца;
3. используют ли `extract_func_def()`, `compute_func_qn()` и
   `cbm_enclosing_func_qn()` один общий результат;
4. существуют ли точные регрессии для `Outer::Inner::method()` и цепочки не менее
   четырёх уровней;
5. проверяет ли полный конвейер `DEFINES_METHOD` по точным QN.

Если upstream уже обходит всю цепочку, подтвердить эквивалентность красно-зелёным
тестом и точными QN. Наличие только рекурсивного поиска конечного `identifier` не
считается достаточным, если владелец по-прежнему содержит лишь первый `scope`.
