# Handoff: Rust `mod` и `impl` используют единый QN типа-владельца

Статус: реализовано в рабочем дереве; целевые регрессии пройдены, общие проверки
имеют зафиксированные независимые блокирующие причины.
Дата фиксации дефекта: 2026-09-01.
Ветка: `v0.10.8-lora`.
Текущая upstream-база: тег `v0.10.8`, коммит
`46ae198fc11cda80e817acbc5f5908d7c2de7032`.
Текущий коммит ветки на момент диагностики:
`7e6ced39826e20ad0dcd00c028230dc00cae81ce`.
Исходная реализация `extract_rust_impl()`: коммит
`59d40d403551f673f51f786e48e5033c434a90e2`
(`v0.5: CBM tree-sitter engine, 59 vendored language grammars`).

## Назначение

Исправить каноническую идентичность Rust-типов и их методов для:

- встроенных модулей `mod name { ... }`;
- квалифицированных `impl module::Type`;
- путей `crate::`, `self::` и `super::`;
- `impl`, вынесенных в другой файл или модуль;
- типов, импортированных перед `impl Type`.

После исправления объявление типа, методы `impl`, области вызовов,
семантические записи и структурные рёбра должны использовать один точный QN
типа-владельца.

## Подтверждённые дефекты

### Встроенные модули отсутствуют в QN

Для допустимого Rust-кода:

```rust
pub mod first {
    pub struct Nested;

    impl Nested {
        pub fn parse(&self) {}
    }
}

pub mod second {
    pub struct Nested;

    impl Nested {
        pub fn parse(&self) {}
    }
}
```

текущий полный индекс создал только один тип и один метод:

```text
Struct: rust.inline.Nested
Method: rust.inline.Nested.parse
parent_class: rust.inline.Nested
```

Сохранённые номера строк относились ко второму модулю. Определения из `first`
были перезаписаны, потому что сегменты `first` и `second` отсутствовали и в QN
типов, и в QN методов.

Единственное оставшееся ребро:

```text
rust.inline.Nested -[:DEFINES_METHOD]-> rust.inline.Nested.parse
```

не доказывает корректность: оно связывает уже схлопнувшиеся узлы.

### Квалифицированный `impl` не совпадает с QN типа

Для однофайлового примера:

```rust
pub mod model {
    pub struct Qualified;
}

impl model::Qualified {
    pub fn parse_qualified(&self) {}
}
```

текущий индекс создал:

```text
type.qualified_name:
rust.qualified.Qualified

method.parent_class:
rust.qualified.model::Qualified

method.qualified_name:
rust.qualified.model::Qualified.parse_qualified
```

`parent_class` не равен QN типа, поэтому `DEFINES_METHOD` отсутствует. В QN типа
потерян встроенный модуль, а в QN `impl` исходный текст `model::Qualified`
добавлен к пути файла как непрозрачное имя.

### Межфайловый `impl` привязывается к файлу реализации

Для файлов:

```rust
// rust/lib.rs
pub mod model;
mod imported_impl;
mod remote_impl;
```

```rust
// rust/model.rs
pub struct Remote;
```

```rust
// rust/imported_impl.rs
use crate::model::Remote;

impl Remote {
    pub fn parse_imported(&self) {}
}
```

текущий индекс создал:

```text
type.qualified_name: rust.model.Remote
method.parent_class: rust.imported_impl.Remote
method.qualified_name: rust.imported_impl.Remote.parse_imported
```

В варианте с явным путём:

```rust
// rust/remote_impl.rs
impl crate::model::Remote {
    pub fn parse_remote(&self) {}
}
```

получены:

```text
method.parent_class: rust.remote_impl.crate::model::Remote
method.qualified_name: rust.remote_impl.crate::model::Remote.parse_remote
```

Оба метода существуют как узлы `Method`, но ни один не имеет
`DEFINES_METHOD` к `rust.model.Remote`.

### Простой однофайловый случай работает

Контрольный пример:

```rust
pub struct Simple;

impl Simple {
    pub fn parse_simple(&self) {}
}
```

создаёт согласованные значения:

```text
rust.simple.Simple
rust.simple.Simple.parse_simple
parent_class=rust.simple.Simple
```

и ожидаемое `DEFINES_METHOD`. Именно этот простой случай покрывают действующие
тесты, поэтому они не обнаруживают дефекты модулей и межфайловых `impl`.

## Условия подтверждённого воспроизведения

Минимальный репозиторий был проиндексирован текущей реализацией через
`index_repository(mode="full")`. Индексация завершилась со статусом `indexed`;
`skipped_count` и `parse_partial_count` были равны нулю.

После индексации проверить типы:

```cypher
MATCH (t)
WHERE (t:Struct OR t:Class OR t:Enum OR t:Trait)
  AND t.file_path STARTS WITH 'rust/'
RETURN t.name, t.qualified_name, t.file_path, t.start_line
ORDER BY t.file_path, t.qualified_name
```

Проверить методы:

```cypher
MATCH (m:Method)
WHERE m.file_path STARTS WITH 'rust/'
RETURN m.name, m.qualified_name, m.parent_class, m.file_path, m.start_line
ORDER BY m.file_path, m.qualified_name
```

Проверить рёбра:

```cypher
MATCH (t)-[:DEFINES_METHOD]->(m:Method)
WHERE m.file_path STARTS WITH 'rust/'
RETURN t.qualified_name, m.qualified_name, m.parent_class, m.file_path
ORDER BY m.qualified_name
```

На неисправной реализации два `Nested` и два `parse` схлопываются, а запрос
рёбер не возвращает квалифицированные и межфайловые методы `Remote` и
`Qualified`.

## Первопричина

### Rust `mod_item` не считается областью QN

`walk_defs()` в `internal/cbm/extract_defs.c` расширяет
`ctx->enclosing_class_qn` только для конструкций, которые распознаёт
`is_namespace_scope_kind()`.

Общий `cbm_is_namespace_scope_kind()` в `internal/cbm/helpers.c` поддерживает
C++/CUDA namespace и TypeScript/TSX namespace, но не Rust `mod_item`.

Поэтому обход проходит сквозь встроенный модуль как через обычный контейнер. Тип
`first::Nested` получает тот же QN из пути файла и короткого имени `Nested`, что
и `second::Nested`.

Добавление Rust только в один из двух предикатов недопустимо: область
определений и унифицированная область вызовов снова разойдутся.

### `extract_rust_impl()` пересобирает владельца из файла реализации

`extract_rust_impl()` в `internal/cbm/extract_defs.c`:

1. Берёт текст поля `type` у `impl_item`.
2. Отрезает обобщённые аргументы по первому `<`.
3. Вызывает `cbm_fqn_compute(ctx->rel_path, type_name)`.
4. Строит `method_qn` как `<type_qn>.<method_name>`.
5. Записывает тот же `type_qn` в `parent_class`.

Этот алгоритм работает только когда тип и `impl Type` находятся в одном файле и
тип записан коротким именем. Он не знает:

- лексический встроенный модуль;
- семантику `crate::`, `self::` и `super::`;
- импорт, приведший короткое имя к типу из другого файла;
- фактический QN узла типа в проектном реестре.

### Область вызовов повторяет неверный владелец

`compute_class_qn()` в `internal/cbm/extract_unified.c` имеет отдельную обработку
Rust `impl_item`, но также читает текст поля `type` и присоединяет его к пути
текущего файла.

После входа в `impl` эта область используется для построения QN вложенных
методов. Следовательно, изменение только `extract_rust_impl()` приведёт к
расхождению `CBMCall.enclosing_func_qn` и QN узла `Method`.

В `push_boundary_scopes()` имеется более поздняя Rust-ветка для `impl_item`, но
она недостижима, когда `impl_item` уже входит в `rust_class_types`: общая ветка
обработки классов выполняется раньше. Сохранять рядом два расходящихся алгоритма
нельзя.

### Семантическая функция не распознаёт владельца `impl`

`cbm_enclosing_func_qn()` в `internal/cbm/helpers.c` обходит предков из
`class_node_types`, но ожидает поле `name`. У `impl_item` имя владельца находится
в поле `type`, поэтому Rust `impl` не добавляет тип к QN этой ветки.

В резервном пути семантическая запись получает файловый QN функции, который не
совпадает даже с текущим методом из `extract_rust_impl()`.

### Граф намеренно требует точного равенства

`process_def()` в `src/pipeline/pass_definitions.c` и
`register_and_link_def()` в `src/pipeline/pass_parallel.c` ищут владельца через
точный `cbm_gbuf_find_by_qn(def->parent_class)`.

Эту точность нужно сохранить. Поиск `Remote` по короткому имени или суффиксу
может связать метод с одноимённым типом из другого модуля.

Для межфайлового случая также нужно учитывать порядок появления узлов: точное
разрешение владельца и создание ребра должны выполняться после того, как
проектный набор типов и импортов доступен целиком.

## Контракт после исправления

Для каждого Rust-метода в `impl` должны выполняться следующие инварианты:

1. QN типа включает полный канонический путь встроенных модулей.
2. `method.parent_class` точно равен QN существующего типа-владельца.
3. `method.qualified_name` начинается с
   `method.parent_class + "."`.
4. Два одноимённых типа из разных Rust-модулей создают разные узлы.
5. Их одноимённые методы также создают разные узлы.
6. `impl Type`, `impl self::Type`, `impl module::Type` и
   `impl crate::module::Type` разрешаются согласно Rust-модулю, а не как
   непрозрачные строки относительно файла реализации.
7. Импортированный тип в `impl Type` разрешается к QN объявления.
8. Обобщённые аргументы не входят в идентичность базового типа, но модульный путь
   не теряется.
9. `CBMCall.enclosing_func_qn` и семантические записи внутри метода точно равны
   QN метода.
10. Для каждого метода существует точное
    `Type -[:DEFINES_METHOD]-> Method`.
11. Собственный `impl Type` и реализация `impl Trait for Type` используют
    реализующий тип как владельца; `trait` остаётся в `impl_trait` и связи
    `IMPLEMENTS`.

Ожидаемые QN основного воспроизведения:

```text
rust.inline.first.Nested
rust.inline.first.Nested.parse

rust.inline.second.Nested
rust.inline.second.Nested.parse

rust.qualified.model.Qualified
rust.qualified.model.Qualified.parse_qualified

rust.model.Remote
rust.model.Remote.parse_imported
rust.model.Remote.parse_remote
```

Точное оформление корня `crate` должно следовать существующему проектному
контракту QN. Токены `crate`, `self` и `super` не должны оставаться литеральными
сегментами после разрешения пути.

## Требуемое устройство исправления

### Единая модель Rust-модуля

Добавить Rust `mod_item` в общий механизм квалифицирующей области и использовать
его согласованно в:

- обходе определений `walk_defs()`;
- унифицированном обходе областей и вызовов;
- вычислении QN типов и функций внутри встроенных модулей;
- определении окружающей функции для семантических записей.

Простого добавления строки в один `if` недостаточно. Определения, вызовы и
семантические записи должны использовать один формат модульного QN.

Проверить также свободные функции внутри `mod`: введение модульной области не
должно оставить их на старом файловом QN, иначе два одинаковых имени функций в
разных модулях продолжат сталкиваться.

### Единый механизм разрешения типа-владельца

Построение владельца `impl` должно быть общим как минимум для:

- `extract_rust_impl()`;
- `compute_class_qn()` в `internal/cbm/extract_unified.c`;
- `cbm_enclosing_func_qn()` или общей функции, которую он вызывает.

Механизм должен принимать текущий модуль, текст или AST пути типа и доступные
импорты. Для межфайлового случая он обязан сопоставить цель с фактическим QN
типа в полном проектном реестре.

Если на стадии файлового извлечения межфайловый тип ещё нельзя разрешить точно,
сохранить структурированную цель `impl` для последующей проектной фазы. Не
подменять неизвестность коротким именем и не создавать окончательный ложный
`parent_class`.

Следует проверить возможность переиспользования действующей Rust LSP-модели в
`internal/cbm/lsp/rust_lsp.c`, включая локальный реестр, обработку импортов и
`rust_process_impl()`. Не копировать большой самостоятельный механизм разрешения
в `extract_defs.c`, если проект уже содержит нужную семантику пути.

### Отложенное точное связывание

После разрешения типа-владельца создать `DEFINES_METHOD` в фазе, где доступны
все узлы типов. Последовательный и параллельный пути должны давать одинаковый
результат независимо от порядка файлов.

Инкрементальный конвейер должен:

- пересвязать методы после изменения файла с типом;
- пересвязать методы после изменения файла `impl`;
- удалить старый ошибочный QN метода, а не оставить два узла.

## Недопустимые обходы

Не исправлять дефект следующими способами:

- удалением квалификатора до последнего имени типа;
- заменой `::` на `.` без разрешения `crate`, `self`, `super` и импортов;
- поиском владельца только по `name = 'Remote'`;
- сопоставлением QN по суффиксу;
- сохранением встроенного модуля только в `parent_class`, но не в QN типа;
- исправлением узла `Method` без согласования вызовов и семантических записей;
- созданием типов-псевдонимов с ошибочными QN;
- специальными правилами для имён `Nested`, `Qualified` или `Remote`.

## Обязательные регрессионные тесты

### Два встроенных модуля с одинаковыми именами

В `tests/test_extraction.c` добавить зарегистрированный тест с `first::Nested` и
`second::Nested`, каждый из которых имеет метод `parse`.

Тест должен:

1. Проверить отсутствие `has_error` и `parse_incomplete`.
2. Найти два узла `Struct` с точными разными QN.
3. Найти два узла `Method` с именем `parse` и точными разными QN.
4. Проверить `parent_class` каждого метода.
5. Проверить QN вызова и хотя бы одной семантической записи внутри каждого
   метода.
6. Проверить свободные одноимённые функции в двух встроенных модулях, если общий
   механизм области затрагивает их QN.

Существующий `mn_module_rust_mod` в `tests/test_matrix_new_constructs.c`
проверяет только минимальное количество функций и не сравнивает QN, поэтому не
заменяет эту регрессию.

### Квалифицированный `impl` в том же файле

Добавить тест для `impl model::Qualified` и проверить точное равенство:

```text
method.parent_class == type.qualified_name
method.qualified_name == type.qualified_name + ".parse_qualified"
```

Проверка по подстроке `Qualified` недостаточна.

### Межфайловые варианты

В `tests/test_edge_structural.c` добавить детерминированный многофайловый тест:

- `lib.rs` объявляет модули тестового `crate`;
- `model.rs` объявляет `Remote`;
- один файл импортирует `Remote` и содержит `impl Remote`;
- другой файл использует явный `impl crate::model::Remote`.

Проверить точные рёбра от одного узла `rust.model.Remote` к обоим различным
методам.

Также проверить отсутствие ошибочных узлов с префиксами файлов реализации:

```text
rust.imported_impl.Remote
rust.remote_impl.crate::model::Remote
```

### Базовые Rust-сценарии

Сохранить и усилить проверки для:

- простого `struct Simple` и `impl Simple` в одном файле;
- `impl Trait for Item`, где владельцем метода остаётся `Item`;
- обобщённого типа-владельца;
- `self::Type` и `super::Type` во вложенном модуле;
- `enum` и других типов-владельцев, поддерживаемых текущим извлекателем.

Текущие `rust_struct` в `tests/test_extraction.c` и `defines_method_rust` в
`tests/test_edge_types_probe.c` проверяют только простой однофайловый случай.
`defines_method_rust` требует наличие хотя бы одного ребра и не проверяет точные
QN владельца и метода.

### Порядок и режим конвейера

Добавить проверки, доказывающие:

- независимость результата от порядка `model.rs` и файлов `impl`;
- одинаковые QN и рёбра последовательного и параллельного путей;
- корректное инкрементальное обновление каждого из файлов;
- удаление старых ошибочных узлов после изменения алгоритма идентичности.

## Результат реализации от 2026-09-01

### Выполненные изменения

- Rust `mod_item` входит в общий механизм лексической QN-области определений,
  вызовов и семантических записей; свободные функции внутри inline `mod` также
  получают модульный сегмент.
- Общие функции `cbm_rust_lexical_module_qn()`,
  `cbm_rust_type_path_qn()` и `cbm_rust_impl_owner_qn()` разрешают bare,
  `crate::`, `self::`, повторяющиеся `super::` и импортированные пути типа.
- Для Rust импорты извлекаются до определений, чтобы `impl Remote` мог
  использовать предшествующий `use`. Один QN владельца применяют
  `extract_rust_impl()`, `compute_class_qn()`, `cbm_enclosing_func_qn()` и Rust
  LSP.
- Последовательный и параллельный пути повторяют точное связывание
  `DEFINES_METHOD` после появления всех узлов. Инкрементальные маршруты сохраняют
  связь при изменении только файла типа или только файла `impl`.
- Добавлены точные проверки inline-модулей, одинаковых имён типов и методов,
  квалифицированного `impl`, путей `self`/`super`, импортированного и
  `crate`-квалифицированного межфайлового `impl`, порядка файлов, параллельного и
  инкрементального путей.

### Полученные результаты проверок

- Исходный красный запуск

## Живая проверка после установки

Установка бинарника, перезапуск процесса и переиндексация пользовательских
проектов требуют отдельного разрешения и не входят автоматически в реализацию
карточки.

После разрешённой установки выполнить полную переиндексацию выбранного
Rust-проекта со встроенными модулями и вынесенными `impl`, затем проверить:

1. Модульные сегменты присутствуют в QN типов и методов.
2. Одноимённые типы и методы разных модулей не схлопываются.
3. `parent_class` квалифицированных и межфайловых `impl` совпадает с QN типа.
4. Все ожидаемые `DEFINES_METHOD` присутствуют.
5. Старые QN относительно файлов реализации отсутствуют.
6. Вызовы и семантические записи используют новые QN методов.

Инкрементальный проход по неизменившимся файлам не считается достаточной
миграцией, потому что старые узлы уже сохранены под другими QN.

## Критерии готовности

- Встроенные модули входят в канонический QN Rust-определений.
- Два одноимённых типа и метода в разных модулях не сталкиваются.
- Все поддерживаемые формы пути `impl` разрешаются к фактическому QN типа.
- Определения, вызовы и семантические записи используют один QN метода.
- Межфайловые `DEFINES_METHOD` не зависят от порядка файлов или режима
  конвейера.
- Собственные `impl Type` и реализации `impl Trait for Type` сохраняют действующее
  семантическое разрешение.
- Новые тесты падают на исходной реализации и проходят после исправления.
- Узкие тесты, линтеры и полный `scripts/test.sh` прошли либо для каждого
  непройденного шага указана блокирующая причина.
- Установка и переиндексация не выполнялись без отдельного разрешения.

## Вне границ доработки

- Полная модель Cargo workspace, не требуемая указанными локальными путями.
- Изменение схемы SQLite или уникального ключа `(project, qualified_name)`.
- Приблизительный поиск типов по короткому имени или суффиксу.
- Общая переработка Rust LSP, не требуемая единым QN владельца.
- Разделение одноимённых методов нескольких `trait`, реализованных одним типом,
  если этот отдельный сценарий не подтверждён новым падающим тестом.
- Изменение пользовательских Rust-репозиториев.
- Автоматическая установка, перезапуск, очистка кэша или переиндексация.

## Восстановление после обновления upstream

При переносе на новую upstream-версию сначала проверить:

1. Входит ли полный встроенный модуль в QN Rust-типа.
2. Разрешается ли цель `impl` к фактическому QN объявления, включая
   межфайловые пути и импорты.
3. Используют ли тот же QN область вызовов и семантические записи.
4. Создаётся ли `DEFINES_METHOD` после появления всех проектных типов.
5. Есть ли точные тесты с одинаковыми именами в разных модулях.

Успешный однофайловый `impl Simple` не является доказательством эквивалентного
исправления.

## Откат

До установки исправление откатывается отменой модульной области Rust, механизма
разрешения типа-владельца, отложенного связывания и новых тестов. После установки и
полной переиндексации откат бинарника также требует полной переиндексации: старый
и новый алгоритмы создают разные QN типов и методов.
