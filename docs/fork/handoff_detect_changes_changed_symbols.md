# Точные изменённые символы в `detect_changes`

Статус: перенесено на `v0.10.8` и проверено.
Дата текущего переноса: 2026-08-23.
Ветка переноса: `v0.10.8-lora`.
Текущая upstream-база: `v0.10.8`
(`46ae198fc11cda80e817acbc5f5908d7c2de7032`).
Исходная база реализации: `v0.9.1-rc.1`
(`ee9833df2c72b750378273897ffec9410fc2c4f2`).

## Назначение

Научить `detect_changes` возвращать точный список функций и методов, исходный
код которых затронут Git-изменениями, вместо отождествления любого изменения
файла с изменением всех определённых в нём символов.

Для получения только этого списка вводится публичный режим
`scope: "symbols"`. Его минимальный ответ содержит:

- выбранную пользователем базу сравнения в поле `base`;
- фактический SHA общей базы в поле `merge_base`;
- полный массив канонических `qualified_name` в поле `changed_symbols`.

По умолчанию элементы `changed_symbols` не содержат метки, пути, номера строк и
другие сведения. Дополнительные поля выдаются только по явному запросу через
`fields`.

Точный `qualified_name`, включая различающие перегрузки C++ параметры и
квалификаторы, остаётся идентификатором символа согласно карточке
[`handoff_cpp_overload_qualified_names.md`](handoff_cpp_overload_qualified_names.md).

## Исходная проблема

До доработки обработчик сначала получал список изменённых файлов, а затем
`detect_collect_seeds()` вызывал `cbm_store_find_nodes_by_file()` и добавлял
почти каждый найденный в файле узел. Исключались только контейнерные метки
`File`, `Folder`, `Project`, `Module`, `Package` и `Section`.

Из-за этого изменение одной функции превращает все функции, методы, классы,
поля и другие определения того же файла в начальные узлы обхода. Для
`scope: "impact"` это раздувает область входящего влияния: в неё попадают
вызывающие символы, код которых в действительности не изменялся.

Кроме того, прежний публичный `inputSchema` перечислял только `files` и
`impact`. Обработчик распознавал строку `symbols` как запрос символов, но не
отделял её от запуска обхода графа влияния и не публиковал как самостоятельный
режим. Ответ показывал только количество `seed_symbols`, поэтому клиент не мог
увидеть, какие именно узлы стали начальными.

## Область доработки

В первой версии изменёнными кодовыми символами считаются узлы с меткой
`Function` или `Method`, которые:

1. существуют в текущем индексе проекта;
2. принадлежат изменённому файлу;
3. имеют корректный диапазон `start_line`–`end_line`;
4. пересекаются с изменённым диапазоном на новой стороне Git-diff.

Конструкторы, деструкторы, операторы и другие конструкции входят в результат,
если существующий извлекатель представляет их узлами `Function` или `Method`.
Карточка не меняет классификацию символов в индексаторе.

Проверка является текстовой: изменение кода, комментария или форматирования
внутри диапазона функции или метода считается изменением символа. Отдельное
сравнение нормализованных AST-поддеревьев в эту версию не входит.

## Публичный контракт MCP

### Запрос только изменённых символов

Основной вызов:

```text
detect_changes({
  project: "/home/slader/Projects/evilcats/dsp",
  since: "HEAD~10",
  scope: "symbols",
  format: "json"
})
```

`project` остаётся обязательным. `since` и `base_branch` сохраняют текущую
семантику: непустой `since` имеет приоритет над `base_branch`; если оба аргумента
не переданы, используется существующая база по умолчанию.

Публичный `scope` получает три значения:

- `files` — существующий режим изменённых файлов;
- `symbols` — база сравнения и точный список изменённых функций и методов без
  обхода графа;
- `impact` — существующий режим анализа влияния, но с точными изменёнными
  символами в качестве начальных узлов.

Отсутствие `scope` сохраняет существующее публичное значение по умолчанию
`impact`. Для получения только списка символов клиент передаёт
`scope: "symbols"` явно.

Аргументы `direction`, `depth` и `limit` не влияют на результат
`scope: "symbols"`. Они сохраняют назначение только для обхода графа влияния.
`changed_symbols` всегда возвращается полностью и не обрезается параметром
`limit`.

### Минимальный JSON-ответ

Без `fields` элементы `changed_symbols` являются строками:

```json
{
  "base": "HEAD~10",
  "merge_base": "57b1c427578173fc64f546237c9164aed66a27fb",
  "changed_symbols": [
    "libs.sniper.http.server.Connection.Connection.cb_writev_int(ev::io&)",
    "libs.sniper.http.server.Connection.Connection.close()"
  ]
}
```

В минимальном ответе `scope: "symbols"` отсутствуют:

- `changed_files`;
- `seed_symbols` и другие отдельные счётчики;
- `direction`, `depth`, `limit` и сведения об обходе;
- метки узлов;
- пути файлов;
- номера строк и диапазоны фрагментов Git-diff;
- исходный код и текст diff.

Если изменённых функций и методов нет, успешный ответ содержит пустой массив:

```json
{
  "base": "HEAD~10",
  "merge_base": "57b1c427578173fc64f546237c9164aed66a27fb",
  "changed_symbols": []
}
```

`base` повторяет фактически выбранный аргумент сравнения после применения
приоритета `since`. `merge_base` содержит точный SHA, относительно которого
вычислен результат. Успешный ответ `scope: "symbols"` не должен молча опускать
`merge_base`: невозможность разрешить базу является ошибкой запроса.

### Управляемые дополнительные поля

Необязательный массив `fields` позволяет запросить только нужные сведения о
каждом символе. В первой версии поддерживаются:

- `label` — метка узла графа;
- `file` — относительный путь файла в репозитории;
- `lines` — текущий диапазон символа как массив `[start_line, end_line]`.

Пример:

```text
detect_changes({
  project: "/home/slader/Projects/evilcats/dsp",
  since: "HEAD~10",
  scope: "symbols",
  format: "json",
  fields: ["label", "file", "lines"]
})
```

При непустом `fields` строки заменяются объектами. Поле `qn` присутствует всегда,
а остальные поля следуют запросу:

```json
{
  "base": "HEAD~10",
  "merge_base": "57b1c427578173fc64f546237c9164aed66a27fb",
  "changed_symbols": [
    {
      "qn": "libs.sniper.http.server.Connection.Connection.close()",
      "label": "Method",
      "file": "libs/sniper/http/server/Connection.cpp",
      "lines": [171, 189]
    }
  ]
}
```

Пустой или отсутствующий `fields` сохраняет минимальный массив строк.
Неизвестное значение `fields` должно приводить к понятной ошибке аргумента, а
не игнорироваться молча.

### Текстовый формат `tree`

`format: "tree"` использует существующий компактный стиль проекта: скаляры
`key: value`, заголовок списка с количеством и строки с отступом из двух
пробелов. Псевдографика `├──` и `└──` не используется.

Минимальный ответ:

```text
base: HEAD~10
merge_base: 57b1c427578173fc64f546237c9164aed66a27fb
changed_symbols: 2
  libs.sniper.http.server.Connection.Connection.cb_writev_int(ev::io&)
  libs.sniper.http.server.Connection.Connection.close()
```

Каждый `qualified_name` занимает одну логическую строку. Значения, которым по
правилам существующего tree-формата требуется экранирование, заключаются в
кавычки. Например, пробел перед cv/ref-квалификатором не превращается в
разделитель столбцов:

```text
changed_symbols: 1
  "libs.sniper.http.client.Request.Request.data() const"
```

При запросе `fields` используется таблица существующего tree-формата:

```text
base: HEAD~10
merge_base: 57b1c427578173fc64f546237c9164aed66a27fb
changed_symbols: 1  (cols: qn label file lines)
  "libs.sniper.http.client.Request.Request.data() const" Method libs/sniper/http/client/Request.cpp 41-57
```

JSON и tree являются двумя сериализациями одной логической модели, но текущая
архитектура MCP не выполняет преобразование JSON в tree. Обработчик строит их
отдельными ветками через `yyjson` и `cbm_sb_t`/`cbm_tree_*`; реализация этой
доработки сохраняет данный подход.

### Влияние на `scope: "impact"`

Обход графа влияния использует тот же полный набор точных изменённых функций и
методов, который возвращает `scope: "symbols"`. Начальные узлы по-прежнему не
входят в `impacted`, а первый уровень вызывающих имеет `hop: 1`.

Существующие `direction`, `depth`, `limit`, `impacted_total`, `impacted`,
`impacted_modules` и `truncated` сохраняют прежнюю семантику. Параметр `limit`
ограничивает только показанные строки влияния и не сокращает набор начальных
символов.

В ответе `scope: "impact"` точный массив `changed_symbols` должен быть доступен
для проверки начальных узлов. Существующие поля ответа режима `impact` сохраняются
для совместимости; минимизация ответа в этой карточке относится к новому
`scope: "symbols"`.

### Поведение `scope: "files"`

Режим `files` и его текущий ответ не меняются. Он не вычисляет символы и не
запускает обход графа.

## Алгоритм определения изменённых символов

### 1. Разрешение базы

Обработчик применяет существующий приоритет `since` над `base_branch`, проверяет
безопасность аргумента и вычисляет:

```text
git merge-base <base> HEAD
```

Полученный SHA становится `merge_base` и единственной воспроизводимой базой для
последующего сравнения.

### 2. Получение итогового Git-diff

Для отслеживаемых файлов нужен единый diff между `merge_base` и текущим
состоянием рабочей копии. Он должен отражать совокупный итог:

- коммитов после `merge_base`;
- изменений в индексе (`staged`);
- изменений рабочей копии вне индекса (`unstaged`).

Git-diff запрашивается без контекстных строк и цветового оформления, например с
эквивалентом следующих параметров:

```text
git diff --unified=0 --no-color --no-ext-diff <merge_base>
```

Конкретная командная строка должна использовать существующий безопасный и
отменяемый механизм запуска Git-команд MCP. Пользовательские значения нельзя
передавать в `shell` без действующей проверки и экранирования.

Файлы со статусом `untracked` отсутствуют в обычном `git diff`. Их список
по-прежнему получается из `git status --porcelain`; каждый новый исходный файл
считается добавленным целиком.

Для переименований используется путь новой стороны. Чистое переименование без
изменения содержимого не создаёт изменённых символов. Переименование вместе с
правкой содержимого обрабатывается по диапазонам новой стороны.

### 3. Разбор диапазонов новой стороны

Из заголовка каждого фрагмента Git-diff извлекаются `new_start` и `new_count`:

```diff
@@ -120,3 +125,5 @@
```

При `new_count > 0` изменённым считается включительный текущий диапазон:

```text
[new_start, new_start + new_count - 1]
```

Несколько фрагментов одного файла сохраняются отдельными диапазонами. Реализация
не должна делать изменённым весь промежуток между несмежными фрагментами.

Фрагмент только с удалением имеет `new_count == 0` и описывает точку удаления
между строками новой версии. Такая точка относится к сохраняющемуся символу,
если она лежит внутри его текущего диапазона. Граничные случаи должны
проверяться отдельными тестами, чтобы удаление между двумя функциями не помечало
обе.

### 4. Получение текущих символов файла

Для каждого файла с изменёнными диапазонами реализация получает текущие узлы
через `cbm_store_find_nodes_by_file()` и оставляет только:

- `Function`;
- `Method`;
- узлы с положительными и согласованными `start_line` и `end_line`.

Диапазоны и канонические QN уже созданы существующими Tree-sitter-извлекателями
при индексации. Поэтому для первой версии не требуется
`ts_tree_get_changed_ranges()` и не вводится второй синтаксический анализатор.

Предусловием точного результата является актуальный индекс текущей рабочей
копии. Доработка использует существующие механизмы демона и watcher-а для
обновления индекса и не вводит отдельную модель хранения исторических деревьев.

### 5. Пересечение диапазонов

Символ считается изменённым, если хотя бы один его текущий диапазон
пересекается хотя бы с одним изменённым диапазоном файла:

```text
symbol.start_line <= changed_range.end_line
&&
changed_range.start_line <= symbol.end_line
```

Пример:

```text
changed_range: 125-129
symbol:        110-148
```

Пересечение непустое, поэтому `qualified_name` символа добавляется в
`changed_symbols`.

Если один фрагмент затрагивает несколько функций или методов, в результат
входят все пересекающиеся символы. Если пересекаются диапазоны вложенных
вызываемых символов, каждый из них считается изменённым: текст его определения
также изменился.

### 6. Дедупликация и порядок

Один символ может пересекаться с несколькими фрагментами, но возвращается один
раз. Дедупликация выполняется по каноническому `qualified_name`, а не по
короткому `name` и не по номеру строки.

Перед сериализацией итоговый массив сортируется лексикографически по
`qualified_name`. Это делает JSON- и tree-ответы стабильными при повторном
вызове и не связывает порядок с номерами строк.

Для `scope: "impact"` идентификаторы узлов из этого же дедуплицированного набора
передаются в существующий единый BFS из нескольких начальных узлов.

## Ожидаемое поведение в особых случаях

### Изменение внутри одной функции

Если в файле определены несколько функций, а фрагмент Git-diff пересекает
только одну, `changed_symbols` содержит только её QN. Остальные функции файла
не становятся начальными узлами обхода графа влияния.

### Сдвиг строк перед функцией

Вставка или удаление строк выше функции меняет её текущие `start_line` и
`end_line`, но не делает изменённым её код. Фрагмент Git-diff находится выше
нового диапазона символа, поэтому пересечения нет и QN не возвращается.

### Перегрузки C++

Каждая перегрузка имеет отдельный канонический QN. Изменение тела
`f(std::string_view)` не добавляет `f(int)`. Аналогично различаются `data()` и
`data() const`, а также `f() &` и `f() &&`.

### Изменение сигнатуры

Если функция сохраняется, но изменение сигнатуры создаёт новый канонический QN,
ответ содержит текущий QN из новой версии. Старый QN не возвращается, поскольку
первая версия не разбирает исторические символы.

### Новый файл

Для файла со статусом `untracked` или добавленного файла все текущие узлы
`Function` и `Method` считаются изменёнными. Контейнерные узлы и другие метки не
добавляются.

### Удаление внутри сохраняющейся функции

Фрагмент только с удалением внутри диапазона функции помечает её как
изменённую, даже если на новой стороне фрагмент не содержит добавленных строк.

### Полностью удалённая функция или файл

Полностью удалённый символ отсутствует в текущем индексе и не возвращается в
первой версии. Для поддержки удалённых QN потребуется получить содержимое файла
из `merge_base`, разобрать его существующим извлекателем и сформировать результат
для старой стороны. Это отдельное расширение.

### Комментарии и форматирование

Комментарий, пробелы или иное текстовое изменение внутри диапазона функции
помечают её как изменённую. Изменение вне диапазонов `Function` и `Method`,
например между двумя определениями, не добавляет символы.

### Чистое переименование файла

Если Git определил переименование и содержимое символов не менялось,
`changed_symbols` остаётся пустым. Перемещение файла может изменить QN только в
той мере, в какой это уже следует из действующего контракта построения QN;
данная карточка не меняет идентичность символов.

### Ошибка разбора или неполный индекс

Карточка не обещает обнаружить символ, которого нет в текущем графе из-за
ошибки чтения, исключения файла или неполного Tree-sitter-разбора. Реализация не
должна создавать QN по имени файла или текстовой эвристике, чтобы скрыть такой
пробел покрытия.

## Точки изменения

- `src/mcp/mcp.c`:
  - описание `detect_changes` и его `inputSchema`;
  - разбор `scope` и `fields`;
  - замена `detect_collect_seeds()` на сбор диапазонов и точных символов;
  - разделение режима `symbols` и запуска обхода графа влияния;
  - JSON- и tree-сериализация `changed_symbols`;
  - использование точного набора узлов как начальных для единого BFS.
- `src/mcp/compact_out.c` и `src/mcp/compact_out.h` — примитивы
  одноколоночного списка с принятым экранированием.
- `tests/test_mcp.c` — проверка опубликованной схемы и точных форматов ответа.
- `tests/test_incremental.c` — сохранение существующего режима по умолчанию.

Схема SQLite, структура `cbm_node_t`, Tree-sitter-извлекатели и построение
`qualified_name` не изменены.

## Обязательные регрессионные проверки

### Публичная схема

1. `scope` публикует ровно `files`, `symbols` и `impact` с понятными описаниями.
2. `fields` публикует `label`, `file` и `lines` как необязательные уникальные
   значения массива.
3. Описание инструмента объясняет, что `symbols` возвращает функции и методы,
   чьи диапазоны пересекаются с diff, а `impact` использует их как начальные
   узлы.
4. Значение по умолчанию `scope` и существующие параметры режима `impact` не
   меняются.

### Точный выбор символов

1. Из двух функций одного файла после изменения тела одной возвращается только
   её QN.
2. Изменение между функциями не возвращает ни одну из них.
3. Вставка строк выше неизменившейся функции не возвращает её QN.
4. Изменение нескольких строк внутри функции возвращает её один раз.
5. Два несмежных фрагмента внутри одной функции не создают дубликат.
6. Один фрагмент, пересекающий две функции, возвращает обе.
7. Фрагмент только с удалением внутри сохраняющейся функции возвращает её QN.
8. Удаление текста между двумя функциями не помечает обе функции.
9. Новый файл возвращает все свои `Function` и `Method`.
10. Полностью удалённая функция не создаёт выдуманный текущий QN.
11. Чистое переименование файла без изменения содержимого не возвращает
    символы.
12. Изменение комментария или форматирования внутри функции считается
    изменением; аналогичная правка вне функций не считается.

### C++ и стабильность QN

1. Изменение только `f(std::string_view)` не возвращает `f(int)`.
2. Изменение только `data() const` не возвращает `data()`.
3. Изменение только `f() &&` не возвращает `f() &`.
4. Сдвиг строк не меняет возвращаемый QN.
5. Переименование параметра возвращает тот же стабильный QN, но сам символ
   считается изменённым, поскольку его текст изменился.

### Форматы ответа

1. Минимальный JSON содержит только `base`, `merge_base` и строковый массив
   `changed_symbols`.
2. Пустой результат содержит `changed_symbols: []`.
3. Без `fields` в элементах нет путей, строк, меток и diff-диапазонов.
4. С `fields: ["label", "file", "lines"]` элементы становятся объектами с
   обязательным `qn` и запрошенными полями.
5. Неизвестное поле отклоняется с понятной ошибкой.
6. Tree-ответ использует существующие отступы, не содержит `├──`/`└──` и
   корректно экранирует QN с пробелами в cv/ref-квалификаторах.
7. JSON и tree возвращают один и тот же отсортированный набор QN.
8. `limit` не обрезает `changed_symbols`.

### Git-состояния и `impact`

1. Учитываются коммиты между `merge_base` и `HEAD`.
2. Учитываются изменения со статусом `staged` в текущей рабочей копии.
3. Учитываются изменения со статусом `unstaged` в текущей рабочей копии.
4. Учитываются файлы со статусом `untracked`.
5. `since` имеет приоритет над `base_branch`.
6. `merge_base` в ответе совпадает с SHA, использованным для diff.
7. `scope: "symbols"` не запускает BFS.
8. `scope: "impact"` запускает единый BFS только от точных
   изменённых символов.
9. Вызывающие неизменённой функции того же файла не попадают в `impact` только
   из-за соседства с изменённой функцией.
10. Начальные узлы отсутствуют в `impacted`, а непосредственные вызывающие имеют
    `hop: 1`.

## Реализация

Публичная схема `detect_changes` теперь содержит режим `symbols` и строгий
массив `fields`. Обработчик получает единый diff без контекстных строк от
разрешённого `merge_base` до текущей рабочей копии, сохраняет фрагменты новой
стороны отдельными диапазонами и выбирает из актуального индекса только
пересекающиеся узлы `Function` и `Method`. Для новых файлов сохраняется
семантика полного файла, а чистое переименование без фрагментов не создаёт
изменённых символов.

Отсортированный и дедуплицированный набор используется одновременно для
`changed_symbols` и, в режиме `impact`, как единственный набор начальных узлов
общего BFS. Режим `symbols` обход графа не запускает.

JSON и tree сериализуются отдельными ветками. В `compact_out` добавлены
минимальные примитивы для заголовка и строк одноколоночного списка; они
используют то же экранирование значений, что и остальные элементы tree-формата.

Реализация находится в следующих файлах:

- `src/mcp/mcp.c` — схема, Git-diff, выбор символов, строгий разбор `fields`,
  сериализация и точные начальные узлы `impact`;
- `src/mcp/compact_out.c` и `src/mcp/compact_out.h` — одноколоночный tree-список;
- `tests/test_mcp.c` — контракт схемы, Git-состояния, диапазоны, C++-перегрузки,
  JSON/tree, `fields`, `limit`, `impact` и сквозная переиндексация;
- `tests/test_incremental.c` — сохранение режима `impact` по умолчанию при
  явной разрешимой базе Git.

## Перенос на `v0.10.8`

В upstream `v0.10.8` не был реализован публичный `scope: "symbols"` с точным
пересечением диапазонов. Кроме того, в новой ветке появилась резервная ветвь,
которая при нулевом пересечении добавляла все символы изменённого файла. Она
противоречит основному контракту карточки и при слиянии не сохранена.

Перенесены публичная схема, JSON- и tree-сериализация, точные diff-диапазоны,
обработка состояний `untracked`, `staged` и `committed`, чистых переименований,
различение C++-перегрузок и использование того же точного набора в качестве
начального для `impact`.
Новый отменяемый механизм запуска внешних команд из upstream при этом сохранён.

В итоговом наборе `mcp` прошли регрессионные тесты
`tool_detect_changes_symbols_selects_exact_ranges_formats_and_impact_seeds`,
`tool_detect_changes_symbols_handles_untracked_staged_committed_and_pure_rename`,
`tool_detect_changes_symbols_distinguishes_cpp_overloads_and_stable_qn`,
`tool_detect_changes_symbols_handles_crossing_hunk_comments_and_deleted_function`

Общий прогон с санитайзерами завершился с кодом `0`:
`2031 passed, 6 skipped`.

## Критерии готовности

- Публичная схема содержит `scope: "symbols"` и управляемый `fields`.
- Минимальный ответ `symbols` содержит только `base`, `merge_base` и полный
  массив QN.
- Изменение одной функции не делает изменёнными остальные функции файла.
- Сдвиг строк выше функции не создаёт ложного изменения.
- Перегрузки C++ различаются по каноническому QN.
- Фрагмент только с удалением внутри сохраняющейся функции обнаруживается.
- JSON и tree соответствуют зафиксированному контракту.
- Обход графа влияния использует только точные изменённые функции и методы.
- Узкие тесты MCP и набор `incremental`, форматирование, Markdown-lint и
  `git diff --check` проходят.
- Выполнена русская редакторская вычитка карточки и описаний MCP.

## Вне границ доработки

- Возврат полностью удалённых символов и разбор старой версии файла.
- Историческое хранение Tree-sitter-деревьев или узлов в SQLite.
- Семантическое сравнение AST с игнорированием комментариев и форматирования.
- Интеграция `sem`, Difftastic, GumTree или другого внешнего diff-инструмента.
- Изменение канонизации `qualified_name` и правил различения перегрузок.
- Добавление отдельного `symbol_id`.
- Изменение графовой схемы, типов рёбер или алгоритма BFS.
- Возврат исходного кода, полного патча или фрагмента Git-diff в минимальном
  ответе.
- Изменение поведения `scope: "files"`.
- Устранение всех возможных пробелов покрытия текущего индексатора.
- Возврат отброшенной реализации `persistence` или блокировок записи БД.

## Восстановление после обновления upstream

Перед переносом на новую базу upstream нужно проверить фактические схему,
описание и обработчик `detect_changes`.

Если upstream уже определяет изменённые функции и методы по диапазонам diff,
нужно проверить эквивалентность следующих свойств, а не переносить старый код
механически:

1. `scope: "symbols"` опубликован и не запускает обход графа влияния.
2. Минимальные JSON- и tree-ответы соответствуют карточке.
3. Начальные узлы обхода графа влияния выбираются по пересечению диапазонов, а
   не по одному имени файла.
4. Перегрузки различаются по каноническому QN.
5. Учитываются изменения в коммитах, а также состояния `staged`, `unstaged` и
   `untracked`.
6. Сохраняются зафиксированные ограничения для удалённых символов и
   косметических изменений.

Если upstream реализовал более сильный механизм на основе AST, его можно
сохранить вместо пересечения диапазонов строк только после проверки того же
публичного контракта и всех обязательных регрессий.

## Откат

Для отката удалить `symbols` и `fields` из публичной схемы, вернуть прежний
выбор всех не-контейнерных узлов изменённого файла и прежние сериализаторы
`detect_changes`. После отката режим `impact` снова будет считать начальными все
символы изменённого файла; это известное прежнее поведение, а не сохранённая
гарантия точности.
