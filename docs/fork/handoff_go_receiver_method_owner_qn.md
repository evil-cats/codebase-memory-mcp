# Handoff: QN методов Go включает тип получателя и сохраняет `DEFINES_METHOD`

Статус: реализовано в рабочем дереве; целевые регрессии пройдены, общие проверки
имеют зафиксированные независимые блокирующие причины.
Дата фиксации дефекта: 2026-09-01.
Ветка: `v0.10.8-lora`.
Текущая upstream-база: тег `v0.10.8`, коммит
`46ae198fc11cda80e817acbc5f5908d7c2de7032`.
Текущий коммит ветки на момент диагностики:
`7e6ced39826e20ad0dcd00c028230dc00cae81ce`.
Источник текущей обработки receiver Go: коммит
`2d772b01bf9e627783aee04fc224f1331e8056e9`
(`Fix extraction/resolution across languages: routing, Go methods, cross-LSP, inheritance, constructors, node kinds`).

## Назначение

Исправить идентичность методов Go, объявленных через receiver, и гарантировать
точное ребро `DEFINES_METHOD` независимо от того, находятся ли тип и его методы
в одном или разных файлах пакета.

После исправления QN метода должен включать QN типа-получателя. Два метода с
одинаковым именем у разных типов одного пакета должны существовать как два
разных узла `Method`, а `parent_class`, QN области вызовов и семантические записи
должны ссылаться на ту же каноническую идентичность.

## Подтверждённые дефекты

### Методы разных типов схлопываются в один узел

Текущий извлекатель строит QN receiver-метода только из каталога пакета и имени
метода. Тип получателя хранится отдельно в `parent_class`, но не входит в
`qualified_name`.

Для допустимого Go-кода:

```go
package sample

type Widget struct{}
type Gadget struct{}

func (w *Widget) Parse() {}
func (g Gadget) Parse() {}
```

оба определения получают один QN:

```text
go.pkg.Parse
```

Уникальный ключ графа не может сохранить два узла с таким QN. В подтверждённом
полном индексе остался единственный узел:

```text
name: Parse
qualified_name: go.pkg.Parse
parent_class: go.pkg.Gadget
```

Определение `Widget.Parse` исчезло, а `parent_class` сохранился от второго
обработанного определения. Это потеря метода, а не только отсутствие удобного
префикса в строке QN.

### Межфайловые `DEFINES_METHOD` не создаются

В том же воспроизведении типы находились в `go/pkg/model.go`, а методы — в
`go/pkg/methods.go`:

```go
// go/pkg/model.go
package sample

type Widget struct{}
type Gadget struct{}
type Box[T any] struct {
    value T
}
```

```go
// go/pkg/methods.go
package sample

func (w *Widget) Parse() {}
func (g Gadget) Parse() {}
func (w *Widget) WidgetOnly() {}
func (g Gadget) GadgetOnly() {}
func (b Box[T]) Value() T { return b.value }
```

Для уникальных методов `parent_class` был вычислен правильно:

```text
go.pkg.WidgetOnly  parent_class=go.pkg.Widget
go.pkg.GadgetOnly  parent_class=go.pkg.Gadget
go.pkg.Value       parent_class=go.pkg.Box
```

Однако в полном графе не было ни одного `DEFINES_METHOD` от этих трёх типов к
методам из отдельного файла. Контрольный однофайловый пример:

```go
package same

type Same struct{}

func (s *Same) SameOnly() {}
```

создал ожидаемое ребро:

```text
go.Same -[:DEFINES_METHOD]-> go.SameOnly
```

Следовательно, простой однофайловый тест не покрывает дефект.

## Условия подтверждённого воспроизведения

Минимальный репозиторий был проиндексирован текущей реализацией через
`index_repository(mode="full")`. Индексация завершилась со статусом `indexed`;
`skipped_count` и `parse_partial_count` были равны нулю.

После индексации проверить методы:

```cypher
MATCH (m:Method)
WHERE m.file_path STARTS WITH 'go/'
RETURN m.name, m.qualified_name, m.parent_class, m.file_path
ORDER BY m.file_path, m.qualified_name
```

Проверить структурные рёбра:

```cypher
MATCH (t)-[:DEFINES_METHOD]->(m:Method)
WHERE m.file_path STARTS WITH 'go/'
RETURN t.qualified_name, m.qualified_name, m.parent_class, m.file_path
ORDER BY m.qualified_name
```

На неисправной реализации первый запрос возвращает только один `Parse`, а
второй не возвращает рёбра для методов из `go/pkg/methods.go`.

## Первопричина

### QN метода не учитывает receiver

`extract_func_def()` в `internal/cbm/extract_defs.c` сначала строит
`def.qualified_name` через `cbm_fqn_compute_source_lang()` из имени функции.

Go-ветка затем:

- распознаёт поле `receiver`;
- меняет `label` на `Method`;
- извлекает тип через `go_receiver_type_name()`;
- правильно записывает QN типа в `def.parent_class`.

При этом `def.qualified_name` не пересобирается. Поэтому `Widget.Parse` и
`Gadget.Parse` остаются одним `go.pkg.Parse`.

Тест `extract_go_no_filename_in_module_qn` в `tests/test_extraction.c` прямо
закрепляет плоский QN `myapp.db.Query`. При исправлении этот тест нужно изменить:
отсутствие сегмента имени файла остаётся правильным требованием, но отсутствие
типа получателя — дефект.

### Область вызовов повторяет плоскую идентичность

`compute_func_qn()` в `internal/cbm/extract_unified.c` не имеет отдельной ветки
для Go receiver. Метод находится на уровне файла, поэтому
`state->enclosing_class_qn` не задан, и функция возвращает пакетный QN с одним
именем метода.

Если изменить только `extract_func_def()`, вызовы внутри метода продолжат
получать старый QN и не смогут точно соединиться с новым узлом `Method`.

### Семантические записи строят третий вариант

`cbm_enclosing_func_qn()` в `internal/cbm/helpers.c` также не распознаёт receiver.
В резервной ветке он вызывает обычный `cbm_fqn_compute(rel_path, name)`, а не
языковой конструктор Go. В зависимости от пути это способно дополнительно
сохранить сегмент имени файла.

Эту функцию используют `CBMUsage`, чтения и записи, назначения типов, исключения
и доступы к окружению. Исправление только узла `Method` оставит семантические
записи на другом QN.

### Структурное ребро создаётся слишком рано

`process_def()` в `src/pipeline/pass_definitions.c` сразу ищет владельца через
точный `cbm_gbuf_find_by_qn(def->parent_class)`. Если тип из другого файла ещё не
находится в текущем графовом буфере, попытка молча заканчивается без ребра.

Последующая фаза этого прохода повторно создаёт межфайловые `IMPORTS`, каналы и
конфигурационные рёбра, но не повторяет `DEFINES_METHOD` после появления всех
типов.

Параллельный путь использует отдельный `register_and_link_def()` в
`src/pipeline/pass_parallel.c`. Исправление обязано сохранить одинаковое
поведение последовательного, параллельного и инкрементального конвейеров.

## Контракт после исправления

Для каждого Go receiver-метода должны выполняться следующие инварианты:

1. `method.parent_class` точно равен `type.qualified_name`.
2. `method.qualified_name` равен
   `type.qualified_name + "." + method.name`.
3. Два типа одного пакета с одноимёнными методами создают разные узлы `Method`.
4. Значение и указатель receiver одного типа используют один QN владельца.
5. Receiver обобщённого типа не переносит параметры типа в QN владельца.
6. `CBMCall.enclosing_func_qn` внутри метода точно равен QN метода.
7. Семантические записи внутри метода используют тот же QN.
8. Существует ровно одно ожидаемое ребро
   `Type -[:DEFINES_METHOD]-> Method` для каждого метода.
9. Ребро не зависит от размещения типа и метода по файлам одного пакета.
10. Свободные функции Go сохраняют пакетный QN без имени файла и без типа.

Для основного воспроизведения ожидаются:

```text
go.pkg.Widget.Parse  parent_class=go.pkg.Widget
go.pkg.Gadget.Parse  parent_class=go.pkg.Gadget
go.pkg.Widget.WidgetOnly  parent_class=go.pkg.Widget
go.pkg.Gadget.GadgetOnly  parent_class=go.pkg.Gadget
go.pkg.Box.Value  parent_class=go.pkg.Box
```

## Требуемое устройство исправления

### Единый конструктор идентичности метода с receiver

Вынести распознавание receiver и построение полного QN владельца в общий код,
который смогут использовать как минимум:

- `extract_func_def()`;
- `compute_func_qn()`;
- `cbm_enclosing_func_qn()`.

Можно перенести или обобщить текущий `go_receiver_type_name()`, но рядом не
должны остаться три независимых алгоритма разбора receiver.

Общий код должен поддерживать:

- `(w Widget)` и `(w *Widget)`;
- receiver без имени `(Widget)` и `(*Widget)`;
- receiver обобщённого типа, например `(b Box[T])`;
- пакетный QN, основанный на каталоге, без сегмента имени `.go`-файла.

После получения QN владельца все три потребителя должны строить один и тот же
`<owner_qn>.<method_name>`.

### Отложенное точное связывание `DEFINES_METHOD`

Создание структурного ребра должно происходить или повторяться после того, как
узлы всех определений доступны в графовом буфере.

Допустимые варианты реализации:

- отдельная вторая фаза для `DEFINES_METHOD` по сохранённым определениям;
- общий отложенный список пар `parent_class` и `method_qn`;
- эквивалентный проектный механизм, сохраняющий точное равенство QN.

Последовательный и параллельный пути должны использовать один контракт и не
расходиться по порядку файлов. Инкрементальный проход должен восстанавливать
ребро после изменения любого из двух файлов.

### Зависимые подсистемы

Проверить и при необходимости согласовать:

- регистрацию методов и `cbm_registry_lookup_method()` в
  `internal/cbm/lsp/go_lsp.c`;
- `check_go_class_implements()` в `src/pipeline/pass_semantic.c`, комментарий
  которого сейчас явно опирается на плоский Go QN;
- создание `IMPLEMENTS` и `OVERRIDE` для неявной реализации интерфейсов;
- разрешение прямых вызовов, selector-вызовов и method expressions;
- удаление старых узлов при инкрементальном обновлении.

Не сохранять плоский QN как узел-псевдоним: это возвращает коллизию, которую должна
устранить доработка.

## Недопустимые обходы

Не исправлять дефект следующими способами:

- добавлением номера строки, имени файла или случайного суффикса к QN;
- сохранением одного `go.pkg.Parse` с несколькими рёбрами владельцев;
- поиском владельца только по короткому имени типа;
- сопоставлением `parent_class` по суффиксу;
- исправлением только `parent_class` или только `DEFINES_METHOD`;
- специальным правилом для имён `Widget`, `Gadget` или `Parse`;
- принудительным объединением файлов пакета в один синтетический исходник.

В `tests/test_extraction.c` добавить зарегистрированный тест с двумя типами
одного пакета и методами `Parse`.

Тест должен:

1. Проверить отсутствие `has_error` и `parse_incomplete`.
2. Найти два, а не один, узла `Method` с именем `Parse`.
3. Проверить точные QN `pkg.Widget.Parse` и `pkg.Gadget.Parse`.
4. Проверить точное равенство каждого `parent_class` QN соответствующего типа.
5. Покрыть receiver по значению и по указателю.
6. Отдельно проверить обобщённый receiver `Box[T]`.
7. Проверить QN вызова и хотя бы одной семантической записи внутри каждого
   метода.

Обновить `extract_go_no_filename_in_module_qn`: новый ожидаемый QN метода должен
быть `myapp.db.Conn.Query`, но в нём по-прежнему не должно быть сегмента
`.conn.`.

### Точное межфайловое ребро

В `tests/test_edge_structural.c` добавить зарегистрированный тест с типами в
`model.go` и методами в `methods.go`.


### Порядок, параллельность и инкрементальность

Добавить проверки, которые доказывают:

- одинаковый результат при перестановке `model.go` и `methods.go` во входном
  списке;
- одинаковые QN и рёбра в последовательном и параллельном конвейерах;
- сохранение ребра после изменения только файла типа;
- сохранение ребра после изменения только файла методов;
- отсутствие старого плоского узла `pkg.Parse` после полного пересоздания
  индекса.

### Сохранение Go-семантики

Существующие тесты должны продолжить покрывать:

- неявную реализацию интерфейса через набор методов;
- `OVERRIDE` от конкретного метода к методу интерфейса;
- встраивание типов и продвигаемые методы;
- наборы методов для receiver по указателю и по значению;
- прямые вызовы, selector-вызовы и method expressions;
- свободные функции пакета.

## Живая проверка после установки

Установка бинарника, перезапуск процесса и переиндексация пользовательских
проектов требуют отдельного разрешения и не входят автоматически в реализацию
карточки.

После разрешённой установки выполнить полную переиндексацию выбранного Go-проекта
с несколькими типами, имеющими одноимённые методы, и проверить:

1. Каждый метод существует отдельным узлом.
2. Старые плоские QN методов отсутствуют.
3. `parent_class` точно совпадает с QN типа.
4. Межфайловые `DEFINES_METHOD` присутствуют.
5. Вызовы, `IMPLEMENTS` и `OVERRIDE` ссылаются на новые узлы.

Инкрементальный проход по неизменившимся файлам не считается достаточной
миграцией: старые плоские узлы уже находятся в сохранённом индексе.

## Критерии готовности

- QN receiver-метода включает полный QN типа и не включает имя `.go`-файла.
- Два одноимённых метода разных типов сохраняются как два узла.
- Определение, область вызовов и семантические записи используют один QN.
- Межфайловые `DEFINES_METHOD` не зависят от порядка файлов или режима
  конвейера.
- Неявные Go-интерфейсы и разрешение методов не сломаны.
- Новые тесты падают на исходной реализации и проходят после исправления.
- Узкие тесты, линтеры и полный `scripts/test.sh` прошли либо для каждого
  непройденного шага указана блокирующая причина.
- Установка и переиндексация не выполнялись без отдельного разрешения.

## Вне границ доработки

- Изменение QN свободных функций Go.
- Добавление имени файла в пакетные QN.
- Изменение схемы SQLite или уникального ключа `(project, qualified_name)`.
- Приблизительное разрешение владельца по имени или суффиксу.
- Общая переработка Go LSP, не требуемая новым контрактом идентичности.
- Изменение пользовательских Go-репозиториев.
- Автоматическая установка, перезапуск, очистка кэша или переиндексация.

## Восстановление после обновления upstream

При переносе на новую upstream-версию сначала проверить:

1. Входит ли тип receiver в QN узла `Method`.
2. Используют ли тот же QN `compute_func_qn()` и
   `cbm_enclosing_func_qn()`.
3. Создаётся ли `DEFINES_METHOD` после появления всех межфайловых определений.
4. Проверяют ли тесты два разных типа с одним именем метода.

Наличие одного `DEFINES_METHOD` в однофайловом примере не является эквивалентным
исправлением.

## Откат

До установки исправление откатывается отменой общего конструктора QN методов Go,
отложенного связывания и новых тестов. После установки и полной переиндексации
откат бинарника также требует полной переиндексации: старый и новый алгоритмы
создают разные QN методов.
