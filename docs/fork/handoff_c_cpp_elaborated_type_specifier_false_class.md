# Handoff: QN типа C/C++/CUDA принадлежит определению с телом

Статус: реализовано; связанные тесты прошли, ограничения общих проверок зафиксированы ниже.
Дата обнаружения: 2026-09-02.
Дата реализации: 2026-09-03.
Ветка: `v0.10.8-lora`.
Текущий коммит ветки на момент диагностики:
`b44215da4471877adc66bdcad8e6744777512067`.
Текущая upstream-база: `v0.10.8`
(`46ae198fc11cda80e817acbc5f5908d7c2de7032`).

## Назначение

Исправить извлечение определений C, C++ и CUDA так, чтобы узел `Class` или
`Enum`, его QN и диапазон исходника создавались только по определению типа с
телом.

Использование `struct Tag`, `class Tag`, `union Tag` или `enum Tag` в типе поля,
переменной, параметра либо возвращаемого значения не должно создавать ложный
`Class` или `Enum`. Предварительные объявления без тела также не должны становиться
самостоятельными `Class` или `Enum`: десять `struct Request;` в разных файлах не
должны создавать десять однострочных классов.

Если определение с телом присутствует в проекте, поиск типа и разрешимые ссылки
должны вести к QN и диапазону именно этого определения. Если определения нет,
тип остаётся неразрешённым; отдельная модель внешних типов или предварительных
объявлений не входит в эту доработку.

Карточка предназначена для агента без контекста текущего разговора. Она задаёт
живое воспроизведение, первопричину, требуемый контракт, тесты и границы
исправления.

## Результат реализации

В `internal/cbm/extract_defs.c` добавлен единый предикат
`class_node_is_indexable_definition()`. Для C, C++ и CUDA он требует тело у
`class_specifier`, `struct_specifier`, `union_specifier` и `enum_specifier`.
Остальные языки сохраняют прежнюю классификацию, а `type_definition` продолжает
обрабатываться отдельно, чтобы фильтр тегов без тела не удалял `typedef`-алиас.

Предикат применяется в трёх местах:

- непосредственно в `extract_class_def()` перед созданием `CBMDefinition`;
- в `push_nested_class_nodes()` до помещения вложенного кандидата в стек;
- в `walk_defs()` до вычисления нового `enclosing_class_qn`.

Последняя проверка важна для предварительного объявления верхнего уровня: узел
без тела проходит обычный обход дочерних элементов в прежнем контексте и не
становится ложной областью видимости.

Добавлены и зарегистрированы регрессии:

- `cpp_elaborated_type_member_does_not_emit_nested_class` в
  `tests/test_extraction.c`;
- `c_struct_tag_member_does_not_emit_nested_class` в
  `tests/test_extraction.c`;
- `pipeline_cpp_forward_declarations_use_definition_qn` в
  `tests/test_pipeline.c`.

C++-регрессия дополнительно покрывает `class`, `union` и `enum`: настоящие
определения с телом сохраняются, а предварительные объявления и употребления
этих типов внутри `Holder` не создают вложенные `Class` или `Enum`.

## Размножение предварительных объявлений между файлами

Предварительное объявление сейчас получает QN, основанный на пути каждого файла.
Поэтому несколько объявлений одного C++-типа не объединяются с его определением,
а создают отдельные узлы `Class`.

Живой пример из `libs/sniper/aerospike`:

```text
AerospikeClient.h:17
libs.sniper.aerospike.AerospikeClient.sniper.aerospike_client.Response

AerospikePromise.h:21
libs.sniper.aerospike.AerospikePromise.sniper.aerospike_client.Response

AerospikeResponse.h:16-58
libs.sniper.aerospike.AerospikeResponse.sniper.aerospike_client.Response
```

Первые два узла созданы по `struct Response;`. Третий содержит настоящее
определение с телом. Между тремя узлами нет связи, которая обозначала бы один
символ или соединяла предварительное объявление с определением.

Дефект влияет не только на выдачу поиска. В подтверждённом индексе первый
однострочный узел имеет четыре входящих ребра, второй — одно, а настоящее
определение — ни одного. Вызовы и использования могут направляться к
предварительным объявлениям вместо определения.

Следовательно, при десяти `struct Request;` в десяти разных файлах текущий
алгоритм обычно создаёт десять однострочных `Class Request` с разными QN. Если
существует отдельное определение с телом, оно становится ещё одним узлом.

После исправления в таком проекте должен существовать ровно один `Class Request`:
его `qualified_name`, `file_path`, `start_line` и `end_line` принадлежат
определению с телом.

## Почему затронут `struct tm`

Tree-sitter не придаёт особого значения именам `ev_loop` и `tm`. В одинаковом
синтаксическом положении обе конструкции дают `struct_specifier`:

```cpp
struct ev_loop* loop;
struct tm* broken_down_time;
```

Поэтому `struct tm* broken_down_time` в поле класса или структуры сейчас также
может создать ложный `Class tm`. Указатель не является причиной: вариант
`struct tm broken_down_time` затронут тем же способом. Вариант
`tm* broken_down_time` без ключевого слова `struct` не создаёт
`struct_specifier` и этим конкретным дефектом не затронут.

## Минимальное воспроизведение C++

Добавить детерминированный тестовый пример без зависимости от DSP:

```cpp
struct Existing {};
struct Forward;
typedef struct Opaque Opaque;

class Holder {
public:
    struct Existing* pointer = nullptr;
    struct Existing value;

    struct Nested {
        int value;
    };

    struct NestedForward;
};
```

До исправления извлекатель создаёт лишние `Class Forward`, `Class Opaque`,
`Class Holder.Existing` и `Class Holder.NestedForward`. После исправления должны
существовать только:

- верхнеуровневые `Existing` и `Holder`, потому что у них есть тела;
- настоящее вложенное определение `Holder.Nested`;
- поля `pointer` и `value` с `parent_class`, равным QN `Holder`.

Узлы `Class Forward`, `Class Opaque`, `Class Holder.Existing` и
`Class Holder.NestedForward` должны отсутствовать. Если `typedef Opaque` по
действующему контракту создаёт отдельный `Type`, этот узел сохраняется: запрет
относится к ложному `Class` тега без тела.

Пример одновременно защищает настоящее определение, предварительные объявления
на двух уровнях, `typedef struct` и использование существующего типа через
указатель и по значению.

## Межфайловое воспроизведение канонического QN

Локальные тесты извлечения доказывают отсутствие отдельных ложных определений,
но не доказывают, что полный конвейер выбирает QN настоящего определения. Для
этого нужен отдельный временный проект.

Создать десять файлов `forward_00.h` — `forward_09.h` с одинаковым содержимым:

```cpp
namespace api {
struct Request;
}
```

Добавить `Request.h` с единственным определением:

```cpp
namespace api {
struct Request {
    int id;
};
}
```

Добавить `Use.cpp` с разрешимым использованием типа, например созданием
объекта:

```cpp
#include "Request.h"

namespace api {
Request* make_request() {
    return new Request{};
}
}
```

После полного прохода должны выполняться все условия:

1. По имени `Request` найден ровно один узел `Class`.
2. Его QN равен `Request.api.Request`: он построен из `Request.h`, пространства
   имён `api` и имени `Request`.
3. `file_path` равен `Request.h`, а `start_line: 2` и `end_line: 4` указывают на
   определение с телом.
4. Ни один `forward_*.h` не создаёт `Class Request`.
5. Разрешимое использование из `Use.cpp` направлено к QN определения, а не к
   отсутствующему QN предварительного объявления.

Если текущий конвейер не создаёт подходящее ребро для `new Request{}`, выбрать
другую детерминированно разрешаемую форму использования C++, уже поддержанную
существующими тестами. Нельзя убирать проверку целевого QN и ограничиваться
только количеством узлов.

## Первопричина

### Один синтаксический вид используется и для объявления, и для типа

В `internal/cbm/lang_specs.c` массивы `cpp_class_types` и `c_class_types`
безусловно относят `struct_specifier`, `union_specifier` и `enum_specifier` к
узлам типов. `cpp_class_types` также содержит `class_specifier`.

CUDA переиспользует C++-массивы, поэтому относится к той же области влияния.

Само включение этих видов необходимо для обнаружения настоящих определений с
телом. Ошибка состоит в отсутствии проверки, что конкретный узел действительно
содержит такое определение.

### Поиск вложенных классов проваливается внутрь полей

`push_nested_class_nodes()` в `internal/cbm/extract_defs.c` проходит внутрь
`field_declaration`, `template_declaration` и `declaration`. Любой дочерний узел,
входящий в `spec->class_node_types`, без дополнительной классификации помещается
в основной стек `walk_defs()` как вложенный класс.

Для строки `struct ev_loop* loop` функция находит `struct_specifier`, хотя тот
является частью типа поля, а не вложенным определением.

### Создание определения не проверяет тело и контекст

`walk_defs()` передаёт каждый такой узел в `extract_class_def()`.

`extract_class_def()` требует только поле `name`. Функция не проверяет:

- есть ли у спецификатора тело;
- является ли узел предварительным объявлением без тела;
- присутствует ли рядом `declarator` поля, переменной, параметра или функции;
- используется ли имя только как спецификатор типа с ключевым словом
  (`elaborated type specifier`).

Если текущий обход уже находится внутри класса, функция добавляет имя к
`ctx->enclosing_class_qn`, после чего безусловно записывает `CBMDefinition`.
Так возникает QN `AerospikeClient.ev_loop`. Для предварительного объявления
верхнего уровня тот же путь строит отдельный QN из пути каждого файла, поэтому
один логический тип размножается между заголовками.

Поле `loop` извлекается другим проходом и остаётся правильным. Поэтому в графе
присутствуют оба узла.

### Это не ошибка форматирования QN

QN механически отражает путь файла и переданный `enclosing_class_qn`. Ошибка
произошла раньше: узел использования типа или предварительного объявления без
тела вообще не должен был попасть в `extract_class_def()` как определение.
Специальное сокращение, перестроение QN или приблизительное объединение по имени
замаскирует дефект, но оставит ложный узел.

## Контракт после исправления

Для C, C++ и CUDA должны выполняться следующие инварианты:

1. `Class` или `Enum` создаётся только для определения типа с телом.
2. Его `qualified_name`, `file_path`, `start_line` и `end_line` принадлежат
   определению с телом, а не предварительному объявлению.
3. Спецификатор без тела, используемый в типе поля, переменной, параметра или
   возвращаемого значения, не создаёт `Class` или `Enum`.
4. Самостоятельное предварительное объявление `struct Forward;`,
   `class Forward;`, `union Forward;`, `enum class Forward;` или
   `enum Forward : int;` без тела не создаёт `Class` либо `Enum`.
5. Несколько предварительных объявлений одного типа в разных файлах не создают
   несколько символов и не конкурируют с настоящим определением.
6. Поля продолжают извлекаться с прежними `qualified_name`, `parent_class` и
   `return_type`.
7. Определение с телом создаёт узел типа, включая форму
   `struct Nested { ... } member` и `typedef struct Named { ... } Named`.
8. `typedef struct Opaque Opaque;` без тела не создаёт `Class Opaque`, но
   существующий узел алиаса `Type`, если он предусмотрен текущим контрактом,
   сохраняется.
9. Разрешимые использования и вызовы указывают на QN определения с телом.
10. Если определения с телом в проекте нет, тип остаётся неразрешённым и не
    подменяется однострочным `Class`.
11. Имена `ev_loop`, `tm`, `Request`, `cbm_watcher` и другие идентификаторы не
    получают специальных правил.
12. Последовательный, параллельный и инкрементальный конвейеры получают одинаковый
    набор определений, поскольку классификация выполняется до сохранения в граф.

Формально некоторые конструкции без тела являются объявлениями типа по правилам
языка. В этой модели метка `Class` означает индексируемое определение, от
которого можно получить тело и полный диапазон. Если предварительные или внешние
объявления понадобятся как самостоятельные сущности, для них потребуется
отдельный тип узла и явная связь с каноническим определением.

## Требуемое устройство исправления

Добавить единый предикат определения типа для C/C++/CUDA. Имя и точная сигнатура
могут следовать стилю проекта, но один алгоритм должен использоваться во всех
путях извлечения определений.

Для `class_specifier`, `struct_specifier`, `union_specifier` и
`enum_specifier` предикат должен требовать настоящее тело. Контекст родителя и
наличие `declarator` больше не превращают спецификатор без тела в `Class`:
предварительное объявление и использование типа одинаково не являются
определениями с телом.

`type_definition` требует отдельной аккуратности:

- `typedef struct Opaque Opaque;` без тела может сохранить узел алиаса `Type`, но
  не `Class Opaque`;
- `typedef struct Opaque { ... } Opaque;` должен сохранить настоящее определение
  структуры с телом и существующий контракт typedef-алиаса;
- анонимные структуры с телом и именованным typedef не должны исчезнуть.

Для обнаружения тела следует переиспользовать существующий
`find_class_body()` или общий эквивалент, а не создавать второй список видов тел.

Проверку нужно применить не позже вызова `extract_class_def()`. Желательно также
не помещать спецификаторы без тела в стек `push_nested_class_nodes()`, но
оптимизация обхода не заменяет защиту в точке создания `CBMDefinition`.

После удаления узлов предварительных объявлений проверить разрешение ссылок на
уровне проекта. Если определение с телом существует в другом файле, реестр и
отложенные проходы должны выбирать его единственный QN. Не добавлять объединение
по суффиксу или короткому имени поверх уже созданных ложных узлов: ложные узлы
необходимо перестать создавать.

Исправление должно охватывать C, C++ и CUDA через общий механизм. Нельзя
добавлять проверку только для `struct_specifier` в одном конкретном файле или
только при наличии указателя.

### Недопустимые обходы

Не исправлять дефект следующими способами:

- фильтрация по именам `ev_loop`, `tm`, `cbm_watcher` или системным заголовкам;
- удаление всех однострочных `Class`;
- подавление только при `pointer_declarator`, поскольку использование по
  значению тоже ошибочно;
- очистка ложных узлов после построения графа по `in_degree == 0`;
- изменение формата QN или дедупликация по короткому имени;
- сохранение предварительных объявлений как `Class` только ради того, чтобы
  резолверу было куда направить ребро;
- создание узлов-алиасов для каждого файла с `struct Request;`;
- связывание нескольких ложных `Class` между собой вместо выбора определения с
  телом;
- исправление только отображения `get_code_snippet` или `search_graph`;
- специальное правило для DSP либо каталогов `libs/sniper`.

### Общий охват спецификаторов типов

Минимально обязательный дефект относится к `struct`. Однако общий предикат

тот же обход. Если реализация отдельно ветвится для `enum_specifier`, добавить
проверку отсутствия ложного вложенного `Enum` при использовании существующего
enum как типа поля.

Недостаточно проверять только количество всех классов: тест должен требовать
отсутствие конкретного ложного QN и присутствие конкретных настоящих QN.
