# Точный диапазон однострочного символа в `get_code_snippet`

Статус: реализовано и проверено.
Дата: 2026-08-06.
Ветка: `v0.9.1-rc.1-lora`.
База апстрима: `v0.9.1-rc.1`
(`ee9833df2c72b750378273897ffec9410fc2c4f2`).

## Назначение

Исправить `get_code_snippet`, чтобы символ с корректным однострочным диапазоном
`start_line == end_line` возвращал только собственную строку. Резервное чтение
следующих строк должно применяться только тогда, когда конечная граница
отсутствует или находится раньше начальной.

## Проявление дефекта

В индексе проекта `/home/slader/Projects/evilcats/dsp` конструктор
`_proto_cache() = default;` представлен отдельным узлом `Method` с точным
диапазоном `81-81`:

```text
search_graph(
    project="/home/slader/Projects/evilcats/dsp",
    name_pattern="^_proto_cache$",
    label="Method",
    fields=["signature"],
    limit=50,
    offset=0,
)
```

Для конструктора найден точный `qualified_name`:

```text
libs.sniper.cache.Cache_int.sniper::cache._proto_cache._proto_cache()
```

Однако следующий запрос:

```text
get_code_snippet(
    project="/home/slader/Projects/evilcats/dsp",
    qualified_name="libs.sniper.cache.Cache_int.sniper::cache._proto_cache._proto_cache()",
    include_neighbors=false,
)
```

возвращал диапазон `81-131`. В `source` попадали не только однострочный
конструктор, но также соседние объявления и определения методов. Фактическое
определение находится в `libs/sniper/cache/Cache_int.h:81` и занимает одну
строку:

```cpp
_proto_cache() = default;
```

`codemapctl bottom-up next` не создаёт ошибочный диапазон самостоятельно, а
передаёт модели координаты, полученные от `get_code_snippet`.

## Причина

`build_snippet_response()` принимал `node->end_line` только при строгом условии
`node->end_line > start`. Равенство границ ошибочно трактовалось как отсутствие
полезного диапазона:

```c
int end = node->end_line > start ? node->end_line : start + SNIPPET_DEFAULT_LINES;
```

`SNIPPET_DEFAULT_LINES` равен `50`, поэтому для начальной строки `81`
вычислялась конечная строка `131`.

Это предположение неверно для корректных однострочных символов, в том числе:

- специальных функций C++, явно объявленных через `= default` или `= delete`;
- однострочных функций и методов других поддерживаемых языков;
- деклараций, для которых точная строка уже сохранена в графе.

Параметр `include_neighbors` управляет только добавлением имён связанных узлов и
не должен влиять на диапазон или содержимое `source`.

## Контракт после исправления

- `start_line == end_line` является корректным однострочным диапазоном.
- При `end_line >= start_line` используются точные границы узла графа.
- Резервные `SNIPPET_DEFAULT_LINES` применяются только при отсутствующей или
  обратной конечной границе: `end_line < start_line` после нормализации начала.
- `include_neighbors=false` не расширяет и не сужает исходный код символа.
- Ограничение `MCP_SNIPPET_MAX_LINES` для чрезмерно больших структурных узлов
  сохраняется без изменений.
- Поиск и разрешение `qualified_name`, подсчёт связей и формат ответа не
  изменяются.

## Состав исправления

- `src/mcp/mcp.c`: принять равные начальную и конечную границы как точный
  диапазон символа.
- `tests/test_mcp.c`: добавить регрессию с однострочным символом и следующей за
  ним контрольной строкой.
- `docs/fork/handoff_get_code_snippet_single_line_range.md`: сохранить описание
  дефекта, контракт и проверки для будущего переноса fork-а.

## Регрессионный сценарий

Тест создаёт индексированный узел `Function` с диапазоном `15-15`. Сразу после
него в исходном файле находится контрольная строка `snippetNeighbor`.

Успешный ответ обязан:

1. вернуть `start_line: 15` и `end_line: 15`;
2. содержать исходный код однострочного символа;
3. не содержать `snippetNeighbor`;
4. сохранять такое поведение при `include_neighbors=false`.

До исправления тест падал: обработчик возвращал `end_line: 65` и захватывал
контрольную строку.

  `snippet_single_line_exact_range` падал на отсутствии точного
  `"end_line":15`; это подтвердило воспроизведение дефекта;
- после исправления набор `mcp` завершился с результатом `188 passed, 2 skipped`;

- локальная конфигурация Markdown-lint в репозитории отсутствует, поэтому

Оба запуска набора `mcp` дополнительно печатали UBSan-диагностику в неизменённом
`src/pipeline/pass_similarity.c:152`. После исправления набор завершился с кодом
`0`; устранение этой отдельной диагностики не входит в область карточки.

## Критерии готовности

- Для корректного узла `N-N` MCP-обработчик возвращает точный диапазон `N-N` и
  не читает следующую строку.
- Регрессионный тест падает без исправления и проходит с ним.
- Существующие тесты `get_code_snippet` и ограничение больших узлов проходят.
- Форматирование C-кода, `git diff --check` и Markdown-lint проходят.
- Карточка прошла русскую редакторскую вычитку.

## Вне границ исправления

- Изменение правил извлечения `start_line` и `end_line` Tree-sitter-проходами.
- Изменение построения или разрешения `qualified_name`.
- Изменение семантики `include_neighbors`.
- Изменение `codemapctl` или его алгоритма `bottom-up next`.
- Пересмотр эвристик объединения деклараций и определений в других инструментах
  MCP.

## Восстановление после обновления апстрима

При переносе на новую версию сначала проверить условие выбора конечной строки в
`build_snippet_response()` и тест однострочного узла. Если апстрим уже отличает
корректный диапазон `N-N` от отсутствующих координат, переносить старую форму
исправления не нужно; достаточно подтвердить контракт регрессионным сценарием.
