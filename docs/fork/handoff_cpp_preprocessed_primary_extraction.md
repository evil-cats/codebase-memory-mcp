Статус: реализовано; собственные регрессии прошли. Общие проверки репозитория
имеют ограничения, перечисленные ниже.
Дата: 2026-09-10.
Ветка: `v0.10.8-lora`.
Коммит исходников MCP при подготовке карточки:
`7b666ff195efd15d05a1091cc1cd137da3a69f31`.

## Назначение и зависимость

Сделать препроцессированный текст основным входом извлечения C++-символов при
пригодном контексте препроцессора. Исходный файл остаётся источником показываемого
кода и исходных координат. Отбор символов не должен зависеть от ограниченного
списка ошибок предварительного разбора оригинала.

Карточка предназначена для реализации без контекста разговора. Она отделяет
проверенные причины потери символов от целевого поведения и ещё не выполненных
проверок. Создание карточки не означает разрешения менять код, устанавливать
бинарник или переиндексировать проекты.

После создания карточки пользователь отдельно разрешил реализацию. Установка,
перезапуск и переиндексация этим разрешением не охвачены.

[Проектные настройки препроцессора][card:cpp-config] уже реализованы. Их формат,
семантика путей, загрузка и передача `cpp.defines` и `cpp.include_paths` принадлежат
прежней карточке и [документации конфигурации][doc:configuration]. Здесь этот
контракт не меняется и не дублируется.

Настройки и порядок извлечения решают разные задачи:

- препроцессор получает макросы из явно переданных определений и доступных
  подключаемых заголовков, а не создаёт недостающий контекст самостоятельно;
- индексатор должен использовать подготовленный результат, не теряя корректно
  распознанные символы при переносе в итоговый граф.

Перенос препроцессинга перед основным извлечением не отменяет необходимость
правильных определений препроцессора и каталогов заголовков.

### Неполный контекст protobuf

Изолированная проверка действующим препроцессором и C++-грамматикой показала:

- без определения версии результат препроцессинга `Au.pb.h` пуст;
- с `PROTOBUF_VERSION=3019000` получено 53 386 байт; тело `class Au` распознано
  на исходных строках 356–568, карта строк этого диапазона корректна;
- при этом `PROTOBUF_NAMESPACE_CLOSE` остался нераскрытым перед `namespace sniper`;
  дерево содержало ложный `function_definition` на строках 80–1753, внутри
  которого оказался класс;
- `walk_defs()` не обходит тела функций в поиске C++-определений, поэтому
  наличие `class_specifier` при произвольном обходе дерева ещё не доказывало
  извлечение `Class Au`.

Каталоги `src` и `libs` не предоставляли требуемый
`google/protobuf/port_def.inc`. На проверенном хосте `/usr/include` содержал

результат. Это наблюдение данного окружения, не универсальный запрет на
системные заголовки.

Для дальнейшей диагностики использован следующий массив `cpp.defines`:

```json

  "PROTOBUF_NAMESPACE_OPEN=namespace google { namespace protobuf {",

  "PROTOBUF_NAMESPACE_ID=google::protobuf"
```

подставлять protobuf-версию либо особые значения для DSP запрещено.

### Ограничение восстановления определений

До исправления в `cbm_extract_file_ex()` оригинал сначала разбирался без подстановки проектных
определений препроцессора. Затем `cbm_preprocess_with_map()` подготавливал второй текст и строилось
второе дерево. Дополнительные определения допускались только при пересечении
с ошибочными областями первого дерева.

В исходном коде:

1. `CBM_MAX_ERROR_REGIONS` ограничивает список 64 областями.
2. `cbm_collect_error_regions()` проверяет дочерние узлы, но не сам переданный
   корень.
3. В проходе восстановления корневой `ERROR` отдельно не добавляется. В отличие
   от него, расчёт покрытия в конце функции явно учитывает такой корень.
4. Класс вне собранных областей отвергается, даже если второе дерево уже содержит
   правильное определение и его исходные координаты восстановлены.

На `src/proto/GoogleRTB.pb.h` подтверждены корневой `ERROR`, 64 собранные области
и конец последней области на строке 2203. Следующий потерянный класс
`BidRequest_Hyperlocal_Point` начинается на строке 2288. Он не может пройти
проверку пересечения с этим списком.

Речь идёт об ошибках разбора оригинала **до** препроцессинга. Успех второго
разбора не очищает первое дерево и не расширяет этот список. Увеличение числа
определений препроцессора поэтому не устраняет данное ограничение.

## Целевое поведение

### Основной проход C++

При пригодном контексте последовательность должна быть такой:

1. Получить исходник и неизменяемый снимок существующих проектных настроек.
2. Выполнить препроцессинг с этими настройками.
3. Разобрать подготовленный текст и извлечь определения и связанные с ними
   сведения из этого представления.
4. Сохранить принадлежность исходному файлу и корректные исходные координаты.

Второе представление больше не является только источником добавок, разрешённых
списком ошибок оригинала. Ошибки первого дерева, их число и достижение лимита
не должны определять право символа попасть в граф.

Подстановка макросов выбирает активные условные ветки. Нельзя безусловно объединять
результат основного прохода с символами всех неактивных веток оригинала. Отдельные
синтаксические ошибки подготовленного дерева также не должны запрещать
извлечение остальных достоверных символов; оставшиеся пробелы отражаются
в диагностике покрытия.

### Исходник, координаты и принадлежность

- Показываемый код, включая `get_code_snippet`, берётся из оригинального файла,
  а не из развёрнутого текста.
- Диапазоны определений, вызовов и употреблений должны соответствовать тому
  представлению, из которого они получены, и корректно переводиться в исходные
  координаты там, где это требуется контрактом.
- Определение из подключённого заголовка нельзя приписывать подключившему его
  файлу. Чтение include-каталога не создаёт дополнительный индексируемый проект.
- При невозможности установить происхождение нельзя публиковать выдуманные
  исходные диапазоны.
- `cached_tree`, `source_origin` и потребители сохранённого дерева должны быть
  согласованы. Нельзя подменить дерево оригинала развёрнутым деревом, оставив
  последующим обработчикам исходный текст с другими смещениями.
- Сохраняется [контракт определения типа с телом][card:type-body]: предварительные
  объявления и употребления типов не создают ложные `Class` или `Enum`.

### Ошибки препроцессинга и резервный разбор

Оригинал сохраняется как резервный источник сведений при невозможности получить
пригодный подготовленный результат. Такой результат нельзя выдавать за успешный
разбор с корректным контекстом компиляции.

Для безопасного основного прохода необходимо различать отсутствие работы для
препроцессора, успешный пустой результат и ошибку. Например, файл целиком под
неактивным `#if` может законно стать пустым; резервный разбор не должен возвращать
его отключённые определения. И наоборот, пустой результат из-за активного
`#error` не доказывает отсутствия символов.

Сам по себе непустой результат не доказывает полноты контекста: пример с
нераскрытым `PROTOBUF_NAMESPACE_CLOSE` это уже показал. Конкретную внутреннюю
модель состояний и условия резервного разбора нужно определить перед реализацией;
новые публичные параметры или поля MCP этой карточкой не задаются.

## Точки реализации и ограничения

- [Основной экстрактор][code:extractor]: порядок проходов, отбор определений,
  ограничение ошибочных областей, итоговые координаты и покрытие.
- [Препроцессор][code:preprocessor] и его
  [контракт результата][code:preprocessor-header]: пригодность результата и
  происхождение развёрнутого текста.
- [Извлечение определений][code:definitions]: владельцы, QN, определения с телом
  и обход классов и методов.
- `src/pipeline/pass_definitions.c`, `src/pipeline/pass_parallel.c`,
  `src/pipeline/pass_calls.c`, `src/pipeline/pass_usages.c`,
  `src/pipeline/pass_semantic.c`, `src/pipeline/pipeline_incremental.c`:
  совместимость маршрутов извлечения и потребителей исходника и дерева.

Не заменять исправление увеличением `CBM_MAX_ERROR_REGIONS`, особым случаем для
`Au`, расширения `.pb.h` или проекта DSP. Число отображаемых диагностических
областей можно ограничивать; извлечение символов не должно от него зависеть.

Область согласованного изменения — основной разбор C++. Общие участки также
используются C и CUDA: их поведение и действующую передачу настроек нельзя
случайно менять. Перенос новой политики на другие языки требует отдельного
явного решения.

Автоматическое получение флагов компилятора, обнаружение системных каталогов заголовков,
новое чтение `compile_commands.json`, установка зависимостей, изменение
protobuf-кода и схемы `.codebase-memory.json` в эту карточку не входят.

## Регрессии и критерии готовности

До изменения основного кода добавить воспроизводимые тесты и подтвердить
красную фазу. Основные регрессии должны работать на небольших локальных тестовых примерах,
без установленного protobuf, Docker, сети и машинных путей DSP.

1. Реалистичный protobuf-подобный заголовок с макросами пространств имён: нужные
   определения поступают из проектного конфига либо локального тестового заголовка.
   Проверяются `Class`, точный QN, методы, их владельцы и `DEFINES_METHOD`,
   а не только наличие узла в синтаксическом дереве.
2. Корневой `ERROR`, более 64 дочерних ошибочных областей и класс после последней
   из первых 64 областей: определение должно попасть в результат.
3. Даже если оригинал можно разобрать без ошибок, проектные определения
   препроцессора должны влиять на основной результат. Выбирается активная ветка,
   и отключённые определения не появляются из безусловного объединения с оригиналом.
4. Подключённый заголовок и макроразвёртка меняют расположение текста: проверяются
   принадлежность файлов, диапазоны и показ исходного кода; чужие определения
   не дублируются под именем включающего файла.
5. Отсутствующие настройки, неполный контекст, активный `#error`, корректный пустой
   результат и файл без работы для препроцессора различаются по смыслу.
   Резервный разбор не скрывает неудачу и не возвращает отключённый код.
6. Полный последовательный, параллельный и инкрементальный маршруты дают
   согласованный набор символов и связей. Изменение проектного конфига не
   переиспользует результаты прежнего контекста.
7. Сохраняются исходные координаты вызовов и употреблений, согласованность
   `source_origin`, кеша деревьев и дальнейшего разрешения связей.
8. Сохраняется защита от ложных классов из предварительных объявлений и
   употреблений типов; связанные регрессии C и CUDA не ухудшаются.

Для реализации начать с целевых наборов тестов через штатную обёртку:

```bash
scripts/test.sh --suites "extraction userconfig pipeline parallel incremental c_lsp mcp"
scripts/lint.sh --ci
git diff --check
```

Не считать прежние успешные прогоны доказательством новой схемы. Если проверка
не выполнена или ограничена окружением, зафиксировать это отдельно. Общий
тестовый маршрут выбирать по реальной области изменения, не переносить
автоматически исключения из прежней карточки конфигурации.

После локальных регрессий повторить извлечение на перечисленных 18 реальных
заголовках: сверить каждое ожидаемое имя, QN, диапазон и связи владельцев.
Для данного снимка ориентир — 233 класса сообщений; любые оставшиеся потери
нужно объяснить отдельно, а не скрывать суммарным ростом числа узлов.
Снижение `parse_partial` само по себе не является критерием готовности.

Установка бинарника, перезапуск MCP и переиндексация DSP выполняются только после
отдельного разрешения. После разрешённой переиндексации подтвердить результат
через MCP, а не переносить успех изолированной пробы на живой граф без проверки.

## Реализованный порядок

Основной проход включается для C++ при наличии хотя бы одного переданного
определения препроцессора или include-каталога. Пустой либо отсутствующий
проектный контекст оставляет прежний порядок разбора. C и CUDA сохраняют прежний
дополнительный проход; общий преобразователь квалифицированных имён также
нормализует допустимые пробелы около `::`, появляющиеся после simplecpp.

`cbm_preprocess_cpp()` различает `CBM_PREPROCESS_UNCHANGED`, `CBM_PREPROCESS_OK`
и `CBM_PREPROCESS_FAILED`. Пустой успешный буфер остаётся результатом, а не поводом
вернуть отключённый код. Недоступный include не запрещает частичное извлечение;
фатальные сообщения simplecpp требуют резервного разбора с `parse_incomplete`.
В этих случаях диапазон диагностики охватывает оригинальный файл целиком.

До основного разбора из подготовленного потока удаляются токены подключённых
файлов. Их макросы уже участвовали в препроцессинге. Карта строк переносит
границы определений и номера строк вызовов в оригинал; точные байтовые позиции
вызовов и употреблений остаются в подготовленном буфере с происхождением
`CBM_SOURCE_ORIGIN_PREPROCESSED`. Ограничение 64 диагностических областей не
участвует в выборе определений основного прохода.

`CBMFileResult.cpp_preprocessed` владеет подготовленным текстом и картой строк
вместе с `cached_tree`. `cbm_file_result_cached_source()` выбирает соответствующий
дереву буфер для обоих маршрутов межфайлового разрешения. Исходные `source` и
`source_len` сохраняют прежний смысл. Результат освобождает дерево, подготовленный
текст и арену; изменённые заголовки включены в зависимости сборки препроцессора.

Оригинал дополнительно предоставляет исходные include-директивы, узлы `Macro`
и доступные комментарии определений. Это описание написанного исходника:
директивы могут относиться и к неактивной ветке. Классы и функции из этого
вспомогательного разбора не добавляются. Показ кода использует оригинальный файл.

Пока нет физической карты пользовательских `#line`, такие входы обрабатываются
через явный резерв. Проверка консервативна: строки, похожие на управляющую
директиву внутри многострочного текста, а также неоднозначное начало директивы
с комментарием или переносом имени тоже могут включить резерв. Переименование
заголовком своих токенов в основной файл также отвергается. Это ограничение
отражается в покрытии, а не скрывается выдуманными координатами.

## Проверка реализации

До изменения основного кода подтверждена красная фаза: потеря поздних классов,
сохранение неактивной ветки, возврат отключённого класса из пустого результата,
прежняя сигнатура и потеря функции, созданной макросом.

Добавлены локальные регрессии для корневого `ERROR` с более чем 64 ошибками,
80 классов, активных веток, состояний препроцессора, include-принадлежности,
исходных строк и точных позиций, подмены файла через `#line`, показа оригинального
вызова макроса через MCP, владельцев методов и межфайловых вызовов. Сквозная
проверка сравнивает последовательный, параллельный и инкрементальный маршруты,
затем изменяет проектный конфиг и сверяется с чистым графом.

Повторное изолированное извлечение на всех 18 заголовках DSP дало **233 из 233**
ожидаемых классов сообщений вместо 62. Для каждого проверены имя, точный QN и
физический диапазон; для 3888 методов внутри этих классов проверены владельцы
и диапазоны, включая конструкторы вложенных `union`. Расхождений не найдено.
Все 18 файлов сохраняют сигнал неполного покрытия из-за недоступных include:
четыре определения не превращают данный контекст в полную модель сборки.

Заключительный прогон штатной команды из критериев готовности выполнен для всех
семи наборов. Все добавленные и изменённые регрессии прошли. Сквозной тест подтвердил
`CBM_INCREMENTAL_ROUTE_CLOSURE_REPAIR` для изменения тела уже известной функции и
`CBM_INCREMENTAL_ROUTE_FORCED_FULL` после смены конфига; в обоих случаях проверены классы,
`DEFINES_METHOD` и `CALLS`. Добавление нового имени для этой проверки не используется:
действующий движок закономерно отклоняет такой частичный пересчёт с причиной
`added_definition_names`.

Общий прогон завершился с кодом 1 по двум незатронутым тестам
`tool_snippet_include_neighbors` и `tool_snippet_neighbors_false` в
`tests/test_incremental.c`. Они требуют прежнее JSON-поле `source` и соседей
символа, тогда как `build_snippet_response()` уже возвращает обычный текст.
Тестовый файл и `src/mcp/mcp.c` совпадают с `HEAD`.
Ранний выход из этих проверок оставляет два ответа без `free`: LeakSanitizer
показал ровно две соответствующие аллокации суммарно на 2368 байт.

UBSan также сообщил о передаче `NULL` в незатронутых участках:
`objectscript_udl/scanner.c:122`, `objectscript_routine/scanner.c:118` и
`src/pipeline/pass_semantic_edges.c:996`, `:1074`. Поэтому общий прогон нельзя
называть чистым по санитайзерам.

`scripts/lint.sh --ci` выполнен повторно. Проверки отсутствия пропусков тестов,
форматирования в области CI и запретов `NOLINT` прошли; `cppcheck` остановился на
прежних `internalAstError` в `internal/cbm/extract_defs.c:3027`,
`internal/cbm/extract_calls.c:2694` и `internal/cbm/extract_unified.c:1778`.
Эти файлы не изменялись. Дополнительная проверка форматирования целых изменённых
файлов обнаружила старые отклонения вне правок в `internal/cbm/lsp/c_lsp.c` и `tests/test_extraction.c`;
они также не исправлялись в этой задаче.

Карточка и `docs/CONFIGURATION.md` прошли смысловую и языковую вычитку,
Markdown-lint с резервной конфигурацией и `git diff --check`. В справочнике
настроек, помимо нового порядка C++, исправлены только пробелы в разделителях
таблиц и переносы строк, необходимые для Markdown-lint; прежнее содержание сохранено.

Рабочий бинарник не устанавливался, MCP не перезапускался, DSP не переиндексировался.
