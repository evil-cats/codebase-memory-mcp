# Локальные `qualified_name` без имени проекта

Статус: реализована и проверена на уровне кода; эксплуатационная проверка не
выполнена.
Дата: 2026-08-03.
Ветка: `v0.9.1-rc.1-lora`.
База апстрима: `v0.9.1-rc.1`
(`ee9833df2c72b750378273897ffec9410fc2c4f2`).

## Назначение

Сделать `qualified_name` локальным идентификатором узла внутри проекта и убрать
из него автоматически вычисленное имя проекта.

Проект и узел должны определяться парой:

```text
(project, qualified_name)
```

Например, функция `detect_file_language` из `src/discover/discover.c` должна
получить следующий `qualified_name`:

```text
src.discover.discover.detect_file_language
```

Имя проекта
`home-slader-Projects-evilcats-codebase-memory-mcp` передаётся отдельно в поле
`project` и не повторяется внутри `qualified_name`.

## Исправляемая проблема

Исходная схема FQN была задана как `project.dir.parts.name`. Конструкторы сначала
добавляют имя проекта, затем относительный путь, имя модуля и имя символа. Так
для короткого символа получается длинное имя:

```text
home-slader-Projects-evilcats-codebase-memory-mcp.src.discover.discover.detect_file_language
```

Имя проекта вычисляется из канонического абсолютного пути репозитория. Поэтому
в QN попадают домашний каталог, промежуточные каталоги и имя рабочей копии, хотя
вызов инструмента MCP уже отдельно указывает проект.

В текущей архитектуре одно и то же пространство имён задаётся несколько раз:

- MCP-инструменты принимают `project`;
- для проекта открывается отдельный файл `<cache>/<project>.db`;
- каждый узел хранит поле `project`;
- уникальность узла обеспечивается ключом `(project, qualified_name)`;
- имя проекта дополнительно включается в сам `qualified_name`.

Последний уровень не нужен для различения узлов, ухудшает читаемость ответа и
делает идентификатор символа зависимым от расположения рабочей копии.

## Новый контракт идентичности

### Поля

- `project` выбирает индекс и пространство имён проекта.
- `qualified_name` однозначно определяет узел внутри выбранного проекта.
- `name` остаётся коротким именем для обнаружения одноимённых символов и
  перегрузок.

`qualified_name` не содержит имя проекта ни в начале, ни в другом служебном
сегменте. Относительный путь, языковые области и каноническая сигнатура C++
сохраняются.

Примеры целевого формата:

```text
src.discover.discover.detect_file_language
internal.cbm.helpers.cbm_fqn_compute
src.buffer.ns.Buffer.data()
src.buffer.ns.Buffer.data() const
src.worker.ns.Worker.run() &&
```

Для C++ и CUDA правила канонической сигнатуры из карточки
`docs/fork/handoff_cpp_overload_qualified_names.md` сохраняются полностью.
Удаляется только проектный префикс. Типы параметров, cv/ref-квалификаторы,
шаблонные параметры и ограничения продолжают различать перегрузки.

### Уникальность

Хранимым ключом идентичности остаётся пара `(project, qualified_name)`. Два
проекта могут содержать одинаковый локальный QN и не должны конфликтовать:

```text
(project-a, src.main.run)
(project-b, src.main.run)
```

Поиск по одному `qualified_name` без проекта больше не имеет права полагаться
на глобальную уникальность. Внутренние API должны либо принимать `project`,
либо явно возвращать неоднозначность.

### Имя проекта

Алгоритм `cbm_project_name_from_path()` не меняется. Вычисленное имя по-прежнему
используется:

- как ключ проекта в MCP;
- как имя файла базы данных;
- в поле `nodes.project` и связанных таблицах;
- для координации демона, блокировок, компонента `watcher` и операций
  индексации.

Изменяется только его участие в `qualified_name` исходных и графовых узлов.

## Построение QN

Обе существующие реализации должны формировать один и тот же локальный QN:

- вариант `cbm_pipeline_fqn_compute()` с выделением результата в куче и
  связанные функции в `src/pipeline/fqn.c`;
- вариант `cbm_fqn_compute()` с выделением через `CBMArena` и связанные функции
  в `internal/cbm/helpers.c`.

Из сигнатур конструкторов следует удалить параметр `project`, а из сборки
сегментов — проектный префикс. Нельзя реализовывать новый контракт передачей
пустой строки вместо проекта: вариант с `CBMArena` при существующем алгоритме
может создать ведущую точку, а вызывающие места продолжат распространять ложное
предположение о составе QN.

Правила относительного пути остаются прежними:

- разделители каталогов преобразуются в точки;
- расширение файла удаляется для модулей и символов;
- полное имя файла сохраняется для узла `File`, чтобы не сталкивались файлы с
  одинаковой основой имени;
- конструктор не добавляет синтетическую ведущую точку, но реальная точка в
  имени dotfile сохраняется: например, `.env.local.__file__`;
- правила `__init__.py`, `index.js`, Java и Go сохраняются;
- номера строк в QN не добавляются.

Служебные узлы `Project` и `Branch` не являются символами исходного кода. Их
идентификаторы должны быть отделены от схемы QN исходного кода и не должны
заставлять остальные узлы сохранять проектный префикс. Выбранные служебные
значения не должны конфликтовать с QN, который может быть построен из исходного
пути и имени символа.

В реализации для них используются отдельные значения:

```text
@cbm/project
@cbm/branch/<slug>
```

## Зависимые подсистемы

### LSP и разрешение вызовов

До доработки часть LSP возвращала QN без проекта, после чего конвейер при промахе
повторял поиск с префиксом `<project>.`. После перехода граф хранит локальные QN,
поэтому эта резервная попытка удалена.

Определения, сырые вызовы, LSP-реестр и рёбра `CALLS` должны использовать один
локальный формат. Нельзя оставлять смешанный режим, в котором часть проходов
создаёт локальный QN, а часть продолжает создавать проектный.

### Хранилище и графовый буфер

- Уникальный индекс SQLite `(project, qualified_name)` сохраняется.
- Все точные запросы к узлу используют оба значения.
- `cbm_store_find_node_by_qn_any()` нужно удалить, заменить вариантом с
  `project` или изменить так, чтобы он не обещал глобальную уникальность.
- Графовый буфер может индексировать локальный QN, поскольку один запуск
  конвейера строит один проект. Если буфер используется с несколькими
  проектами, его ключ также должен стать составным.
- Инкрементальная индексация должна удалять прежний узел по локальному QN и не
  оставлять проектно-квалифицированный дубль.

### Архитектурный анализ

`cbm_qn_to_package()` и `cbm_qn_to_top_package()` раньше пропускали первый
сегмент как имя проекта. После изменения обе функции работают с локальным QN,
но сохраняют различие своих контрактов:

- `cbm_qn_to_package()` возвращает ближайший пакетный сегмент и сохраняет
  прежний результат после удаления проектного префикса: для
  `internal.store.search.Search` это `store`;
- `cbm_qn_to_top_package()` возвращает первый локальный сегмент: для того же QN
  это `internal`.

Тесты покрывают корневые и вложенные пути.

### Межпроектные связи

`cross-repo-intelligence` продолжает выбирать исходный и целевой проекты
отдельно. Сопоставление узлов между базами должно переносить пару
`(target_project, target_qualified_name)`, а не восстанавливать проект из QN.

Синтетические QN маршрутов и каналов, которые уже не содержат проектный
префикс, сохраняют текущий формат. Межпроектные свойства рёбер
`target_project` и аналогичные поля не удаляются.

## Поведение MCP

### `search_graph`

- Возвращает локальный `qualified_name` без имени проекта.
- В плоском ответе поле `qn` содержит локальное имя.
- В сгруппированном ответе `qn_prefix` начинается с относительного пути или
  языковой области, а полный QN по-прежнему составляется как
  `qn_prefix + "." + qn_suffix`.
- `qn_pattern` применяется к локальному QN.
- `name_pattern` продолжает искать по короткому `name`.

Для рассматриваемого символа ожидается группа следующего вида:

```text
src.discover.discover:
  detect_file_language
```

### `get_code_snippet` и `trace_path`

Оба инструмента принимают пару:

```text
project = home-slader-Projects-evilcats-codebase-memory-mcp
qualified_name = src.discover.discover.detect_file_language
```

Точный локальный QN выбирает один узел или одну перегрузку. Короткое неоднозначное
имя по-прежнему возвращает список кандидатов, но QN кандидатов также локальны.

Полный прежний QN с проектным префиксом не является новым каноническим форматом.
Скрытая нормализация старого значения не должна подменять миграцию индекса и не
должна возвращать проектно-квалифицированный QN обратно клиенту.

### `query_graph` и другие ответы

Свойство `qualified_name` в графе хранится локальным, поэтому `query_graph`,
архитектурные ответы, подсказки ошибок, кандидаты разрешения и результаты
поиска должны показывать один и тот же формат. Только обрезать строку на границе
`search_graph` недостаточно.

## Миграция существующих индексов

Изменение затрагивает ключ каждого узла, построенного из исходного кода.
Существующая база с проектно-квалифицированными QN несовместима с новым
форматом.

После установки нового бинарника требуется:

1. завершить или перезапустить старые клиентские процессы и демон;
2. выполнить полную переиндексацию каждого проекта новым бинарником;
3. не использовать инкрементальный проход как замену полной миграции;
4. проверить через `search_graph`, что старый префикс не сохранился.

Реализация не должна допускать смешанную базу, где одновременно присутствуют
`project.src.main.run` и `src.main.run`. Если текущий механизм публикации полного
индекса не гарантирует замену поколения целиком, необходимо добавить явное
распознавание несовместимого формата и требование полной переиндексации.

Реализация записывает в `PRAGMA user_version` версию формата QN
`CBM_QN_FORMAT_VERSION = 1`. База без этого маркера считается устаревшей:
инкрементальный путь для неё не используется, вместо него строится и публикуется
полное поколение.

## Итог реализации

- Параметр `project` удалён из обоих семейств конструкторов QN и всех их
  вызывающих мест. Варианты с кучей и `CBMArena` формируют одинаковые локальные
  значения.
- Java, Kotlin, Rust, Python, Go, PHP и Perl переведены на локальные модульные и
  символьные QN. Для корневого модуля Java и Go не создаётся ведущая точка.
- Удалена резервная LSP-попытка найти `<project>.<callee_qn>`; определения,
  вызовы и рёбра `CALLS` используют один локальный формат.
- Точный поиск в хранилище выполняется по `(project, qualified_name)`;
  `cbm_store_find_node_by_qn_any()` удалён. Одинаковый локальный QN разрешён в
  разных проектах.
- `Project` и `Branch` используют служебные QN `@cbm/project` и
  `@cbm/branch/<slug>`, отделённые от пространства исходных узлов.
- Прямой модуль записи SQLite сохраняет версию формата QN, а pipeline отправляет
  базу прежнего формата на полную переиндексацию.
- Ответы `search_graph`, кандидаты неоднозначности, `get_code_snippet` и
  `trace_path` проверены с локальными QN. Точный QN C++-перегрузки выбирает одну
  сигнатуру и один путь вызовов.
- Полный pipeline проверяет SQL-инвариант: ни один построенный исходный узел не
  начинается с `<project>.`.

## Обязательные регрессионные проверки

1. `cbm_pipeline_fqn_compute()` и `cbm_fqn_compute()` возвращают одинаковые
   локальные QN без ведущей точки и без проектного префикса.
2. Модули, каталоги, корневые файлы, `__init__.py`, `index.js`, Java и Go
   сохраняют прежнюю структуру после удаления только проектного сегмента.
3. Два проекта с одинаковым локальным QN сохраняют два разных узла благодаря
   ключу `(project, qualified_name)`.
4. `search_graph` не выдаёт имя проекта в `qn`, `qn_prefix` или `qn_suffix`.
5. `get_code_snippet` находит символ по локальному QN и выбранному `project`.
6. `trace_path` строит путь только для узла, выбранного локальным QN и проектом.
7. Кандидаты при неоднозначности содержат локальные QN.
8. C++-перегрузки `f(int)` и `f(std::string_view)`, `data()` и
   `data() const`, `f() &` и `f() &&` остаются отдельными узлами.
9. LSP-разрешение вызовов не создаёт проектно-квалифицированные дубли и
   сохраняет рёбра `CALLS` для C/C++, Python, TypeScript, Go, Java и Kotlin.
10. `cbm_qn_to_package()` и `cbm_qn_to_top_package()` корректно работают с
    локальными QN.
11. Инкрементальная индексация после изменения сигнатуры удаляет старый
    локальный QN.
12. `cross-repo-intelligence` продолжает создавать межпроектные рёбра и хранит
    имя целевого проекта отдельно от QN.
13. После полной переиндексации в базе отсутствуют QN узлов, построенных из
    исходного кода и начинающихся с `<project>.`.

## Критерии готовности

- `qualified_name` узла, построенного из исходного кода, не содержит имя
  проекта.
- `project` остаётся обязательным отдельным пространством имён.
- Хранилище различает одинаковые локальные QN разных проектов.
- Все проходы индексатора, LSP и MCP используют один локальный формат.
- C++-перегрузки сохраняют каноническую идентичность.
- Полная переиндексация не оставляет узлы старого формата.
- Связанные тестовые наборы, форматирование, статический анализ изменённых
  файлов и Markdown-lint проходят.

## Вне границ доработки

- Изменение алгоритма `cbm_project_name_from_path()`.
- Переименование проекта, файла базы данных или поля `project`.
- Изменение канонической C++-сигнатуры перегрузок.
- Удаление относительного пути из QN.
- Добавление отдельного сохраняемого `symbol_id`.
- Изменение схемы синтетических `Route` и `Channel` без необходимости для
  локальных QN.
- Автоматическая установка бинарника или удаление пользовательского кэша.

## Восстановление после обновления upstream

При следующем обновлении upstream сначала проверить фактическую схему QN,
конструкторы обоих семейств и ответы MCP. Если upstream уже хранит локальный QN
и использует составную идентичность `(project, qualified_name)`, переносить
доработку повторно не нужно.

Если upstream изменил только формат ответа `search_graph`, но продолжает хранить
проектный префикс в графе, это не считается эквивалентной реализацией: нужно
повторно оценить хранилище, LSP, `query_graph` и миграцию индекса.

## Откат

Для отката вернуть проектный сегмент в оба семейства конструкторов QN и во все
зависимые разрешения. После отката также требуется полная переиндексация:
локальные и проектно-квалифицированные QN нельзя безопасно смешивать в одном
поколении базы.
