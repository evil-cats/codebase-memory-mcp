# Handoff: дочерний Linux-процесс закрывает унаследованные fd через `close_range`

Статус: реализовано; функциональные проверки пройдены, полные проверки имеют
зафиксированные независимые ограничения.
Дата диагностики: 2026-09-03.
Ветка: `v0.10.8-lora`.
Исходный коммит: `d3086e8e379e5d64a4425b0e486c81bf162b031d`.
Текущая база `upstream`: тег `v0.10.8`, коммит
`46ae198fc11cda80e817acbc5f5908d7c2de7032`.

## Назначение

Устранить длительный Linux-интервал между `fork()` и `execvp()` в общем
слое `subprocess`. Сейчас дочерний процесс по одному вызывает `close()` для
каждого номера fd от `3` до `_SC_OPEN_MAX`, даже если почти все номера не открыты.

На Linux нужно закрывать диапазон одним системным вызовом
`close_range(3, UINT_MAX, 0)`. Если системный вызов недоступен или завершился
ошибкой, должен выполняться прежний цикл как безопасный резервный путь.

На остальных платформах текущий механизм не меняется. Исправление не отключает
`watcher`, не меняет его интервалы и не убирает необходимые дочерние процессы.

Карточка предназначена для агента без контекста исходного разговора. Она
фиксирует живое наблюдение, первопричину, согласованный контракт реализации,
обязательные тесты и границы изменения.

## Короткий вывод

Периодически появляющийся процесс
`codebase-memory-mcp --cbm-daemon-internal` не является новым MCP-клиентом или
вторым демоном. Это дочерний процесс работающего демона после `fork()`, который
ещё не дошёл до `execvp("git", ...)` и поэтому сохраняет имя и командную строку
родителя.

Длительная видимость процесса вызвана не Git, а почти миллионом бесполезных
`close(fd)` перед `execvp()`:

```text
фактический _SC_OPEN_MAX: 1000000
открытых fd у демона:           17
```

Один опрос `watcher` запускает три последовательные Git-команды. Поэтому процесс
обычно появляется сериями по три экземпляра.

Во время диагностики работали:

- один демон с аргументом `--cbm-daemon-internal` и `PPID=1`;

PID являются только примером конкретного запуска и не должны использоваться в

1. Родителем каждого краткоживущего процесса является демон.
2. Процессы появляются по три последовательно.
3. До `execvp()` они сохраняют исполняемый файл и `argv` родителя.
4. Во время опроса без изменений журнал демона не получает новых строк.

Пятнадцатисекундная синхронная проверка показала две такие серии, а число строк
`cbm-daemon.log` осталось неизменным: `19798 -> 19798`. Следовательно, это не
подключения клиентов и не переиндексация, а успешные проверки Git, которые
журнал не записывает.

## Зачем демон запускает эти дочерние процессы

Если `auto_watch=true`, полноценная MCP-сессия регистрирует существующий
проиндексированный проект в общем `watcher` демона. Значение `auto_watch` по
умолчанию равно `true`.

`watcher` должен обнаруживать изменения рабочего дерева, выполненные вне MCP:

- `git rev-parse HEAD` обнаруживает смену коммита, `checkout`, `pull` и другое
  перемещение HEAD;
- `git status --porcelain -uall -z` обнаруживает изменения, удаления и новые
  файлы до `commit`;
- `git submodule foreach --quiet --recursive ...` учитывает изменения внутри
  подмодулей.

Эти команды запускаются через `watcher_git_run()` и общий
`cbm_subprocess_spawn()`. Только изменение HEAD или сигнатуры состояния рабочего
дерева приводит к `watcher.changed` и последующей индексации. Опрос без изменений
всё равно должен выполнить Git-команды, иначе демон не сможет узнать, что
состояние изменилось.

## Почему период похож на пять секунд

В `src/watcher/watcher.c` базовый интервал равен `5000 ms`. К нему добавляется
секунда на каждые 500 отслеживаемых файлов, предел равен `60000 ms`.

На момент диагностики:

| Проект | Отслеживаемых файлов | Расчётный интервал |
| --- | ---: | ---: |
| `codebase-memory-mcp` | 2062 | `9000 ms` |
| `codex` | 6911 | `18000 ms` |

Общий `watcher` просыпается с базовым шагом, а проекты имеют разные моменты
следующего опроса. Их дочерние процессы могут чередоваться, из-за чего в списке
процессов виден приблизительно пятисекундный ритм.

Интервалы и состав проверок Git не являются дефектом этой карточки.

## Первопричина

### Дочерний процесс после `fork()` наследует отображаемое состояние родителя

На Linux `cbm_subprocess_spawn_posix()` вызывает `fork()`. До успешного
`execvp()` дочерний процесс наследует исполняемый файл, `argv` и открытые
дескрипторы демона.
Поэтому `ps` и `htop` отображают его как
`codebase-memory-mcp --cbm-daemon-internal`.

Это ожидаемая семантика `fork()` и не означает запуск ещё одного MCP-клиента.

### Закрытие унаследованных fd необходимо

Перед `execvp()` код перенаправляет:

- `stdin` в `/dev/null`;
- `stdout` и `stderr` в заданный файл журнала либо `/dev/null`.

Затем необходимо закрыть остальные fd. Иначе внешний процесс может унаследовать
MCP-транспорт, SQLite-дескрипторы, файлы блокировок, сокеты демона или журналы.
Такое наследование способно удерживать ресурс после завершения владельца и
нарушать изоляцию дочернего процесса.

Защитный инвариант правильный и должен сохраниться полностью.

### Текущий алгоритм делает почти миллион системных вызовов

`src/foundation/subprocess.c:cbm_subprocess_spawn_posix()` получает верхнюю
границу так:

```c
long max_fd = sysconf(_SC_OPEN_MAX);
if (max_fd < 0 || max_fd > 1048576L) {
    max_fd = 65536L;
}
```

Значение `1000000` не превышает порог и передаётся в
`cbm_posix_child_exec()`, где выполняется:

```c
for (int fd = STDERR_FILENO + 1; fd < max_fd; fd++) {
    (void)close(fd);
}
```

Каждый `close()` является отдельным переходом в ядро. Почти все вызовы получают
`EBADF`, но всё равно требуют перехода в ядро. До завершения цикла дочерний процесс
ещё не сделал `execvp()` и остаётся видимой копией демона.

Три проверки Git последовательно повторяют эту работу. Наблюдаемый интервал между
появлениями процессов составлял примерно `0.35-0.5 s`, то есть один опрос терял
около полутора секунд ещё до полезной работы Git.

## Согласованное исправление

### Linux

Вынести закрытие fd в небольшую вспомогательную POSIX-функцию и на Linux сначала
выполнять один системный вызов:

```c
close_range(STDERR_FILENO + 1, UINT_MAX, 0);
```

Допустима реализация через прямой `syscall(SYS_close_range, ...)`, чтобы сборка
не зависела от наличия обёртки libc. Проект уже использует этот шаблон
переносимой реализации для системных вызовов, специфичных для Linux.

Требования:

1. Первый fd равен `STDERR_FILENO + 1`, то есть `3`.
2. Последняя граница равна `UINT_MAX`, а не текущему `_SC_OPEN_MAX`.
3. `flags` равен `0`.
4. Не использовать `CLOSE_RANGE_CLOEXEC` или `CLOSE_RANGE_UNSHARE`: контракт
   требует фактического закрытия fd перед запуском внешней программы.
5. Вызов выполняется после `dup2()` и закрытия временных исходных fd, но до
   `execvp()`.
6. Успех `close_range` немедленно завершает очистку без числового цикла.
7. Любая ошибка быстрого пути Linux приводит к прежнему циклу `close()`; нельзя
   продолжать к `execvp()` с потенциально унаследованными fd.
8. Если `SYS_close_range` отсутствует в заголовках при сборке, используется
   прежний цикл.
9. Между `fork()` и `execvp()` не добавлять выделение памяти в куче, операции
   `stdio`, общий механизм журналирования или другие функции без гарантий
   безопасности после `fork()`.

Рекомендуемая форма:

```c
static void cbm_posix_close_inherited_fds(long max_fd) {
#if defined(__linux__) && defined(SYS_close_range)
    if (syscall(SYS_close_range, (unsigned int)(STDERR_FILENO + 1), UINT_MAX, 0) == 0) {
        return;
    }
#endif
    for (int fd = STDERR_FILENO + 1; fd < max_fd; fd++) {
        (void)close(fd);
    }
}
```

Имя вспомогательной функции может следовать стилю файла. Существенны границы
диапазона, нулевое значение `flags`, резервный путь и безопасность после `fork()`.

Если проектные заголовки требуют, добавить только платформенно ограниченные
`<sys/syscall.h>` и заголовок, предоставляющий `UINT_MAX`. Не вводить
Linux-зависимость в Windows-ветку.

### Остальные платформы

- macOS и другие POSIX-платформы сохраняют существующий числовой цикл там, где
  используется резервный путь с `fork()`;
- основной Apple-путь через `posix_spawn` не менять;
- Windows-путь со списком разрешённых дескрипторов не менять;
- не добавлять `/proc/self/fd`, команды оболочки или стороннюю зависимость.

## Почему не следует просто уменьшать `max_fd`

Нельзя заменять верхнюю границу числом реально открытых fd или небольшим
константным пределом. Дескрипторы могут быть разреженными: процесс способен иметь
один открытый fd с большим номером. Пропуск такого fd нарушит защитный контракт.

`close_range(3, UINT_MAX, 0)` одновременно сохраняет полноту очистки и убирает
пользовательский цикл по пустому пространству номеров.

## Почему `FD_CLOEXEC` не является полной заменой

Последовательная установка `FD_CLOEXEC` при создании каждого fd полезна, но не
заменяет финальную очистку:

- новое место вызова может забыть установить флаг;
- библиотека может открыть внутренний fd;
- цель этого слоя — централизованная защита перед любым внешним исполняемым файлом.

Доработка сохраняет существующую эшелонированную защиту, а не переносит
ответственность на всех создателей fd.

## Регрессионные тесты

### Сохранение защитного контракта

Существующий тест
`subprocess_posix_child_closes_unrelated_descriptors` обязан проходить без
изменения смысла. Он снимает `FD_CLOEXEC` с контрольного fd, запускает `/bin/sh`
через общий слой `subprocess` и проверяет, что дочерний процесс не видит
дескриптор.

Тест должен выполняться:

- через быстрый путь Linux;
- через принудительный резервный путь;
- на остальных POSIX-платформах через прежний цикл.

Если существующий тест переиспользуется через вспомогательную функцию, каждая
ветка должна иметь отдельное диагностируемое имя или проверку, чтобы быстрый путь
Linux нельзя было случайно не выполнить.

### Доказательство выбора `close_range`

Добавить тест, выполняемый только на Linux, например
`subprocess_linux_child_uses_close_range_before_exec`. Он должен доказывать сам
выбор механизма, а не только итоговое отсутствие fd: старый цикл также закрывает
контрольный fd и потому не создаёт красной фазы для дефекта производительности.

Предпочтительный способ — узкий тестовый механизм под `CBM_ENABLE_TEST_SEAMS`:

1. Родитель включает запись выбранной стратегии перед запуском процесса.
2. Дочерний процесс сообщает фиксированный маркер через уже перенаправленный
   `STDERR_FILENO` с помощью `write()`.
3. Тест читает журнал дочернего процесса и требует маркер быстрого пути Linux.
4. Рабочая сборка не содержит включённого наблюдения и не пишет маркер.

Допустим другой детерминированный тестовый механизм, если он не ослабляет рабочий
код и не использует время выполнения как единственное доказательство.

### Принудительный резервный путь

Добавить тест, выполняемый только на Linux, например
`subprocess_linux_close_range_failure_falls_back`. Тестовый механизм должен
заставить быстрый путь вернуть ошибку, эквивалентную `ENOSYS`, после чего тест
проверяет:

1. Выполнена резервная ветка.
2. Контрольный fd без `FD_CLOEXEC` не наследуется внешней программой.
3. Дочерний процесс нормально доходит до `execvp()` и завершается с ожидаемым
   кодом.

Тестовая инъекция действует только при `CBM_ENABLE_TEST_SEAMS`, наследуется через
`fork()` и сбрасывается после теста. После `fork()` разрешены только операции,
совместимые с существующим ограничением `async-signal-safety`.

### Другие платформы

На POSIX-платформах кроме Linux тест закрытия контрольного fd должен продолжить
проходить через числовой цикл. Специфичные для Linux тесты должны использовать
явный пропуск по платформе, а не падать при отсутствии `SYS_close_range`.

Windows-тесты и сериализация командной строки не меняются.

### Не использовать хрупкий тест времени

Нельзя считать достаточным тест вида «запуск быстрее N миллисекунд». Нагрузка CI,
санитайзеры и эмуляция делают абсолютный порог нестабильным. Измерение времени
допустимо как дополнительное измерение, но красная/зелёная регрессия должна
наблюдать выбранную ветку непосредственно.

### Дополнительная Linux-проверка механизма

Если в окружении доступен `strace`, полезно подтвердить системные вызовы на
коротком примере запуска дочернего процесса:

```text
ожидается: один close_range(3, UINT_MAX, 0)
не ожидается: сотни тысяч close(...)=EBADF
```

`strace` не является обязательной зависимостью тестов. Его отсутствие не должно
менять реализацию или приводить к установке пакетов без разрешения.

После запуска демона с исправленным бинарником повторить наблюдение за его
дочерними процессами. Дочерние процессы Git сохраняются, но окно, в котором
процесс после `fork()` виден как `codebase-memory-mcp --cbm-daemon-internal`,
должно стать практически мгновенным. Это дополнительная проверка во время
работы, а не замена тестов.

В рамках реализации рабочий бинарник не собирался, не устанавливался и демон не
перезапускался. Поэтому повторное измерение задержки на живом `watcher` пока не
выполнено: тесты непосредственно доказывают выбор одного системного вызова и
резервной ветки, но не являются измерением производительности после установки.

## Критерии готовности

- Linux использует `close_range(3, UINT_MAX, 0)` до `execvp()`.
- Успешный быстрый путь не выполняет числовой цикл `close()`.
- Ошибка или отсутствие системного вызова Linux на этапе компиляции приводит к
  прежнему циклу.
- Остальные платформы сохраняют существующий механизм.
- Контрольный fd без `FD_CLOEXEC` не наследуется дочерним процессом во всех
  применимых ветках.
- Специфичный для Linux тест непосредственно доказывает выбор быстрого пути.
- Принудительный резервный путь доказан отдельной регрессией.
- Между `fork()` и `execvp()` не добавлены небезопасные операции.
- `watcher`, Git-команды, интервалы, переиндексация и логирование не изменены.
- Узкие и полные тесты, lint, `git diff --check` и Markdown-lint прошли либо для
  каждого ограничения записана точная независимая причина.
- Рабочий бинарник, установка, перезапуск демона и переиндексация не выполнялись
  без отдельного запроса.

## Недопустимые обходы

Не исправлять наблюдение следующими способами:

- отключением `auto_watch` по умолчанию;
- увеличением интервала `watcher`;
- удалением `git status`, проверки HEAD или подмодулей;
- переименованием дочернего процесса после `fork()` либо сокрытием процесса только
  в интерфейсе;
- снижением `_SC_OPEN_MAX` до произвольной константы;
- закрытием только известных fd демона по текущему списку;
- надеждой исключительно на `FD_CLOEXEC`;
- использованием оболочки для перечисления или закрытия fd;
- добавлением зависимости от `/proc/self/fd` вместо `close_range`;
- удалением резервного пути на старом Linux или других POSIX-платформах;
- тестом производительности с единственным абсолютным временным порогом.

## Вне границ исправления

- Изменение политики `auto_watch` и конфигурационного значения по умолчанию.
- Изменение формулы адаптивного интервала опроса.
- Уменьшение числа проверок Git за один опрос.
- Замена `fork/exec` всей Linux-реализации на `posix_spawn`.
- Рефакторинг общего контроля дочерних процессов, сроков ожидания, отмены или
  контракта групп процессов.
- Исправление отдельных прежних ошибок `worker` с `exit_code=127` для `Common`.
- Изменение времени жизни демона, клиентских `lease` или MCP-протокола.
- Сборка, установка либо перезапуск бинарника.

## Восстановление после обновления `upstream`

После обновления базы проверить:

1. Как `cbm_subprocess_spawn_posix()` создаёт дочерний процесс на Linux.
2. Закрывает ли `upstream` все fd выше `STDERR_FILENO` одним системным
   примитивом.
3. Сохраняется ли резервный путь при отсутствии быстрого пути.
4. Проходит ли `subprocess_posix_child_closes_unrelated_descriptors`.
5. Есть ли детерминированное доказательство выбора быстрого пути Linux.

Если `upstream` перешёл на `posix_spawn` с корректным действием `close-from` или
другой эквивалент, переносить старый `close_range` механически не нужно. Сначала
доказать те же свойства: отсутствие наследования fd, отсутствие цикла до
`_SC_OPEN_MAX` и сохранение контракта контроля дочерних процессов.

До установки откат состоит в удалении быстрого пути Linux и новых тестов: прежний
числовой цикл функционально корректен, но возвращает диагностированную задержку.

Исправление не меняет формат индекса или хранимые данные, поэтому откат не
требует переиндексации проектов.
