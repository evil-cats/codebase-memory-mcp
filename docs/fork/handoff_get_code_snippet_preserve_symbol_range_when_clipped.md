# Полный диапазон символа при усечении `get_code_snippet`

Статус: реализовано в рабочем дереве; набор `mcp` прошёл.
Дата обнаружения: 2026-09-02.
Дата реализации: 2026-09-02.
Ветка: `v0.10.8-lora`.
Текущий коммит ветки на момент диагностики:
`49545d218a97b62e49202107c1e0479728bd47de`.
Текущая upstream-база: `v0.10.8`
(`46ae198fc11cda80e817acbc5f5908d7c2de7032`).

## Назначение

Исправить `get_code_snippet`, чтобы поля `start_line` и `end_line` всегда
описывали полный диапазон найденного символа. Ограничение
`MCP_SNIPPET_MAX_LINES` должно усекать только поле `source`, не изменяя
координаты символа в ответе.

Карточка предназначена для агента без контекста текущего разговора. Она задаёт
воспроизведение, требуемый контракт, минимальную область изменения и проверки.

## Проявление дефекта

В индексе проекта
`home-slader-Projects-evilcats-codebase-memory-mcp` функция
`src.mcp.mcp.handle_detect_changes` имеет следующий сохранённый диапазон:

```text
file:       src/mcp/mcp.c
start_line: 10862
end_line:   11393
span:       532 строки
```

Диапазон можно проверить через `query_graph`:

```cypher
MATCH (n:Function)
WHERE n.qualified_name = 'src.mcp.mcp.handle_detect_changes'
RETURN n.qualified_name, n.file_path, n.start_line, n.end_line, n.lines
```

Вызов:

```text
get_code_snippet(
    project="home-slader-Projects-evilcats-codebase-memory-mcp",
    qualified_name="src.mcp.mcp.handle_detect_changes",
    include_neighbors=false,
)
```

возвращает:

```text
start_line:       10862
end_line:         11361
source_clipped:   true
clipped_at_lines: 500
```

Поле `source` действительно содержит первые 500 строк функции, то есть диапазон
`10862-11361`. Однако исходная конечная граница символа `11393` в ответе
теряется. По одному результату `get_code_snippet` вызывающая сторона больше не
может узнать полный диапазон найденного символа.

## Ожидаемое поведение

Для того же узла ответ обязан содержать:

```text
start_line:       10862
end_line:         11393
source_clipped:   true
clipped_at_lines: 500
```

Поле `source` по-прежнему должно содержать только первые 500 строк символа.

Смысл полей должен быть однозначным:

- `start_line` и `end_line` — полный нормализованный диапазон символа из
  индекса;
- `source` — доступный исходный код символа, ограниченный
  `MCP_SNIPPET_MAX_LINES`;
- `source_clipped=true` — признак того, что `source` не покрывает весь диапазон
  символа;
- `clipped_at_lines` — максимальное число строк, помещённых в `source`.

Добавлять `source_start_line`, `source_end_line`, параметры диапазона, курсор
или пагинацию не требуется. Текущий API всё равно не позволяет запрашивать
следующую часть исходника, а задача пользователя — получить точные координаты
символа.

## Причина

Дефект находится в `build_snippet_response()` в `src/mcp/mcp.c`.

Одна переменная `end` одновременно используется как:

1. полная конечная граница символа;
2. конечная строка чтения `source`;
3. значение поля ответа `end_line`.

Текущая последовательность имеет следующий смысл:

```c
int end = node->end_line >= start
              ? node->end_line
              : start + SNIPPET_DEFAULT_LINES;

if (end - start + 1 > MCP_SNIPPET_MAX_LINES) {
    end = start + MCP_SNIPPET_MAX_LINES - 1;
    snippet_clipped = true;
}

source = resolve_snippet_source(root_path, node->file_path, start, end, ...);
yyjson_mut_obj_add_int(doc, root_obj, "end_line", end);
```

После ограничения `end` уже не содержит конечную границу символа. Несмотря на
это, именно изменённое значение сериализуется в `end_line`.

Комментарий рядом с кодом утверждает, что точный диапазон остаётся в
`start_line/end_line`, но фактическая реализация этому утверждению противоречит.

## Почему существующий тест не обнаружил дефект

Тест `tool_get_code_snippet_clips_whole_file_node` в `tests/test_mcp.c` создаёт
узел `Module` с диапазоном `1-2000` и проверяет ограничение ответа.

Комментарий теста требует сохранить точный диапазон, но проверки подтверждают
только следующее:

- присутствует `source_clipped=true`;
- ответ не содержит весь файл;
- первая строка присутствует;
- последняя строка отсутствует.

Тест не проверяет `start_line`, `end_line` и `clipped_at_lines`. Поэтому он
проходит с ошибочным `end_line: 500` вместо `end_line: 2000`.

## Требуемое исправление

В `build_snippet_response()` необходимо разделить конечную границу ответа и
конечную строку чтения исходника. Например:

```c
int reported_end =
    node->end_line >= start ? node->end_line : start + SNIPPET_DEFAULT_LINES;
int source_end = reported_end;

bool snippet_clipped = false;
if (source_end - start + 1 > MCP_SNIPPET_MAX_LINES) {
    source_end = start + MCP_SNIPPET_MAX_LINES - 1;
    snippet_clipped = true;
}

char *source =
    resolve_snippet_source(root_path, node->file_path, start, source_end, &abs_path);

yyjson_mut_obj_add_int(doc, root_obj, "start_line", start);
yyjson_mut_obj_add_int(doc, root_obj, "end_line", reported_end);
```

Имена локальных переменных могут отличаться. Обязательное свойство решения:
ограничение чтения не должно изменять сериализуемую границу символа.

Поведение резервного диапазона при `node->end_line < start`, исправленное ранее
поведение однострочного диапазона `start_line == end_line` и значение
`MCP_SNIPPET_MAX_LINES` менять не нужно.

## Регрессионный тест

Расширить `tool_get_code_snippet_clips_whole_file_node` в `tests/test_mcp.c`.
Для существующего узла с диапазоном `1-2000` тест обязан проверить:

1. ответ содержит `"start_line":1`;
2. ответ содержит `"end_line":2000`;
3. ответ содержит `"source_clipped":true`;
4. ответ содержит `"clipped_at_lines":500`;
5. `source` содержит `line_0000` и `line_0499`;
6. `source` не содержит `line_0500` и `line_1999`.

До исправления новая проверка `"end_line":2000` обязана падать, потому что
обработчик возвращает `"end_line":500`.

Отдельный тест параметров диапазона не нужен: таких параметров у
`get_code_snippet` нет и данное исправление их не добавляет.

## Реализация в рабочем дереве

В `src/mcp/mcp.c` функция `build_snippet_response()` теперь использует две
независимые конечные границы:

- `reported_end` сохраняет полный нормализованный диапазон символа и
  сериализуется как `end_line`;
- `source_end` ограничивается `MCP_SNIPPET_MAX_LINES` и используется только для
  чтения `source`.

В `tests/test_mcp.c` существующая регрессия
`tool_get_code_snippet_clips_whole_file_node` дополнительно проверяет полный
диапазон `1-2000`, лимит 500 строк и точную границу возвращённого текста между
`line_0499` и `line_0500`.

Красная фаза подтверждена до исправления рабочего кода: новое утверждение об
`"end_line":2000` падало, потому что обработчик возвращал усечённую границу.
После разделения границ набор `mcp` завершился с результатом
`211 passed, 6 skipped`.

## Связанная карточка

`docs/fork/handoff_get_code_snippet_single_line_range.md` защищает другой край
того же контракта: корректный однострочный символ не должен расширяться до
резервного диапазона. Новая карточка не заменяет и не ослабляет эту регрессию.

После обоих исправлений действует единое правило:

- точные координаты символа сохраняются в `start_line/end_line`;
- объём `source` ограничивается отдельно.

- `source_clipped` и `clipped_at_lines` присутствуют только при фактическом
  усечении;
- символы длиной не более 500 строк сохраняют прежний ответ.

## Критерии готовности

- `start_line` и `end_line` описывают полный диапазон символа независимо от
  ограничения `source`.
- Для диапазона `1-2000` возвращается `end_line: 2000`, но в `source` остаются
  только первые 500 строк.
- Регрессионный тест падает до исправления и проходит после него.
- Существующие тесты точного однострочного диапазона проходят без изменений.
- Публичные аргументы `get_code_snippet` и набор полей ответа не расширяются.
- Значение `MCP_SNIPPET_MAX_LINES` не меняется.
- Набор `mcp`, форматирование, `git diff --check` и Markdown-lint проходят.
- Карточка прошла русскую редакторскую вычитку.

## Вне границ исправления

- Добавление `start_line`, `end_line`, `offset`, `limit`, курсора или пагинации
  в аргументы `get_code_snippet`.
- Возможность получать вторую и последующие части усечённого `source`.
- Добавление `source_start_line` или `source_end_line` в ответ.
- Изменение лимита `MCP_SNIPPET_MAX_LINES`.
- Изменение извлечения координат символов Tree-sitter-проходами.
- Изменение формата `qualified_name` или разрешения символов.
- Изменение клиентского токенного лимита MCP-ответов в Codex.

## Восстановление после обновления апстрима

После обновления сначала проверить `build_snippet_response()` и тест
`tool_get_code_snippet_clips_whole_file_node`.

Если апстрим уже использует разные значения для полной конечной границы символа
и конечной строки чтения `source`, подтвердить контракт регрессионным тестом и
не переносить старую реализацию механически.

Если одна переменная по-прежнему ограничивается до 500 и затем сериализуется в
`end_line`, перенести разделение границ и проверки из этой карточки.
